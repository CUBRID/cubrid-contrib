# cub_ctv — 크리티컬 섹션 뷰어 (신규)

## 1. 목적 (Purpose)

cub_server 의 크리티컬 섹션(서버 내부 R/W 래치 18종)이 *지금 무엇이 잡혀 있고 무엇이 대기 중인지*를,
서버에 접속하지 않고 보여 주는 진단 보조 유틸리티를 추가한다.

현재 이 정보를 보는 방법은 `SHOW CRITICAL SECTIONS` 하나다.
이 명령은 DBA 로 접속해야 하고, 한 번 찍은 스냅샷이며, 소유자를 스레드·트랜잭션 *번호*로만 준다.
엔진 성능 통계(statdump)에는 크리티컬 섹션 항목이 없어 시간에 따른 변화를 볼 수 없다.
또 접속 과정 자체가 크리티컬 섹션을 지나므로, 서버가 크리티컬 섹션에서 멈춘 경우에는 SHOW 를 실행할 수 없다.

| 질문 | cub_ctv 의 답 |
|---|---|
| 어느 크리티컬 섹션에서 대기가 생기는가 | 18종의 순간 상태·대기자 수·누적 진입/대기 횟수·누적/최대 대기 시간 |
| 대기가 일시적인가 계속되는가 | 100Hz 샘플링으로 구간별 점유율·대기율·초당 진입/대기 횟수·초당 손실 시간 |
| 지금 잡고 있는 것은 누구인가 | 트랜잭션 번호 + user@host, program, pid, login, IP, trid, 스레드 번호(엔진 스레드는 OS 스레드 이름) |
| 누가 기다리고 있는가 | promoter·writer 대기 큐 전체 체인 (스레드·트랜잭션·클라이언트) |
| 무엇이 원인인가 | 터미널 요약 화면의 판정 표: 손실이 가장 큰 크리티컬 섹션, 쥔 쪽, 피해 세션, 쥔 스레드의 디스크/CPU 상태, 확인할 것 |
| 크리티컬 섹션 밖이면 어디인가 | 스레드 대기 사유 집계(락·페이지 래치·빈 버퍼·크리티컬 섹션 …) |
| 서버가 접속을 받지 못할 때도 볼 수 있는가 | 볼 수 있다 — /proc 읽기만 하므로 접속 불필요 |
| 접속 없이 트랜잭션 목록을 볼 수 있는가 | `--trans`: `cubrid tranlist` 와 같은 목록 + login·IP |
| 모니터링에 넣을 수 있는가 | `--json`: 스냅샷 1문서, 라이브는 구간마다 1줄 |
| 현장 상태를 나중에 다시 볼 수 있는가 | `--record` 로 본 화면을 기록, `--replay` 로 서버 없이 같은 화면 재생; `--dump` 는 그 순간 읽을 수 있는 정보 전부를 JSON 으로 |

대상 사용자:
접속 폭주·커밋 지연·서버 무응답의 원인을 찾는 기술지원·DBA, 엔진 내부 경합을 이해하려는 개발자.
판정은 엔진 지표와 함께 하며, cub_ctv 는 그 근거를 보충하는 자료를 만든다.

대표 사용 시나리오

| 시나리오 | 확인하는 것 | 다음 조치 | 이 도구를 쓰는 이유 |
|---|---|---|---|
| 커밋 지연 (DML 폭주, 로그 플러시·체크포인트 스톨) | LOG 점유율·대기율, 쥔 쪽이 엔진 스레드(log-flush)인지 클라이언트인지, 쥔 스레드의 디스크 대기 비율 | 엔진이면 로그 디스크·`log_buffer_size`, 클라이언트면 해당 세션 확인 | SHOW 는 한 순간만 보여 주며, 소유자가 ms 단위로 바뀌어 매번 다르게 보인다 |
| 접속 폭주·DDL 반복 | LOCATOR_CLASSNAME_TABLE·TRAN_TABLE·ACCESS_STATUS·CT_OID_TABLE 의 초당 진입/대기 | 애플리케이션 접속 방식·DDL 빈도 점검 | 진입이 많을 뿐인지(고회전) 실제로 막히는지(대기율·손실)를 구분 |
| 아카이브 로그 경합 (백업·CDC) | LOG_ARCHIVE 의 소유자 | 아카이브를 잡은 작업 확인 | 소유자를 신원으로 바로 보여 준다 |
| 서버 무응답 | 대기자가 계속 있는데 진입이 0 인 크리티컬 섹션, 그 소유자와 대기 큐; 깨끗하면 스레드 대기 사유 | 소유 세션 특정 후 조치, 아니면 락·페이지 래치·I/O 쪽 | 접속이 안 되므로 SHOW·tranlist 를 쓸 수 없다 |

범위 밖: 느린 질의, 행 락 경합, 페이지 래치 경합, 버퍼 부족은 크리티컬 섹션 밖의 문제다. 그때 cub_ctv 는
"크리티컬 섹션 경합 없음"과 스레드 대기 사유만 보여 주며, 그것으로 한 영역을 배제한다.

## 2. 설계 원칙 (Design Principles)

| 원칙 | 구현 |
|---|---|
| 서버 무접속 | SQL 접속·cubrid 유틸리티 호출 없음. `/proc/<pid>/maps` 와 대상 메모리 읽기(`/proc/<pid>/mem` pread, 여러 작은 범위는 같은 권한의 `process_vm_readv`)와 procfs 텍스트만 사용 |
| 쓰기 0 / 락 0 | 대상 파일은 전부 `O_RDONLY`, ptrace attach 없음, 서버를 멈추지 않는다. 읽는 동안 커널이 대상 주소공간 잠금(mmap_lock)을 읽기 모드로 잠깐 잡는다 — 주소공간 변경과만 겹친다(부록 B) |
| 자기 영향 0 | SHOW 는 실행 자체가 카운터를 올린다. cub_ctv 의 연속 두 번 판독 사이에 움직인 카운터 0 (백그라운드가 움직이는 LOG·LOG_ARCHIVE·TRAN_TABLE 제외, 실측, t2) |
| 헤더 의존 0 | CUBRID 헤더를 쓰지 않는다. 심볼은 대상이 올린 libcubrid.so 에서 자체 ELF 파서로 찾고, 구조체 위치는 실행 시 메모리 값의 성질(불변식)로 찾는다. 찾은 위치에서 고정 거리로 유도하는 오프셋은 §5 유도식 항목에 열거 |
| 검증 없이 값을 내지 않음 | 불변식 21개(I-0~I-20, 부록 A). 필수 구조가 실패하면 실패한 불변식 번호와 함께 거부하고, 부가 정보가 실패하면 그 정보만 끄고 `layout:` 줄에 표기한다. 검증 못 한 값은 `-` 로 표시 |
| 의존 0 | C, libc 외 의존 없음. 정적 바이너리 하나 |

## 3. 아키텍처 (Architecture)

### 3.1 판독 경로

```text
/proc/<pid>/maps → libcubrid.so 위치 → 자체 ELF 파서 (.dynsym + .symtab)
                     csectgl_Critical_sections  크리티컬 섹션 배열 18개
                     sync_Stats                 동기화 통계 풀 (RWLOCK/RMUTEX/MUTEX 포함)
                     log_Gl                     → 트랜잭션 테이블 → 클라이언트 정보
                     cubthread::Manager         → 스레드 엔트리 배열 (소유자 스레드·대기 큐·대기 사유)
/proc/<pid>/mem  → ctv_mem.c 한 곳 → 프로브(불변식) → 레이아웃
                                                       │
                     라이브 샘플러(100Hz) ─────────────┤── 스냅샷 1회
                                                       ▼
                               view_capture: 프레임(화면 한 장의 모든 답, 한 시점)
                                ├ 표시 (요약 화면 / 표 / --detail / --trans / --json)
                                ├ --record (CTVREC 5 텍스트 기록) ──► --replay → 같은 표시 코드
                                └ --dump   (그 순간 정보 전부의 JSON, 재생 불가)
```

표시 코드는 프레임에서만 답을 받으므로, 같은 보기 옵션이면 라이브 출력과 그 기록의 재생 출력이 바이트 단위로 같다(스크롤·스냅샷 출력 기준, t7; 터미널 요약 화면은 하단 조작 안내 줄만 다름).

### 3.2 구조체 위치를 찾는 방법

| 대상 | 불변식 | 실패 시 |
|---|---|---|
| 크리티컬 섹션 배열 간격·개수 | `cs_index` 가 0,1,2,3… 순서이고 이름이 ASCII 문자열 (I-0~I-2) | 거부 |
| 통계 포인터 위치 | 모든 항목에서 통계의 type 이 CSECT 이고 이름 포인터가 같다 (I-3) | 거부 |
| rwlock·소유자·대기 큐 | 통계 위치에서 유도한 뒤 대기 수 범위·대기 큐 포인터 범위·`rwlock<0 ⇒ owner≠0` 로 교차검증 (I-4) | 거부 |
| 트랜잭션 테이블 | `tdes[k].tran_index == k` (I-6~I-8) | 트랜잭션 기능 끔 |
| 클라이언트 정보 | 문자열 6개 + pid 형태(libstdc++ 구/신 문자열 형식 모두), 다른 디스크립터 증인으로 재확인 (I-9~I-11) | 후보 기각 |
| 동기화 통계 풀 | 청크 엔트리 type 범위·사용 수·다음 포인터 (I-12) | 풀 생략 |
| 스레드 엔트리 배열 | index 가 1,2,3,4 순서 (I-14) | 스레드 정보 끔 |
| 스레드의 tran_index·m_id·OS tid | 값 범위·스레드 수·`/proc/<pid>/task` 대조 (I-15~I-17) | 그 정보만 끔 |
| 대기 사유·실행 상태·대기 링크 | 값 분포 + 런타임 대조(대기 큐 머리는 대기 코드여야 함) (I-18~I-20) | 그 정보만 끔, 필요 시 재탐색 |

전체 원장은 부록 A.

### 3.3 라이브 샘플링

| 항목 | 내용 |
|---|---|
| 샘플링 | 기본 100Hz (`--hz`), 매 샘플은 크리티컬 섹션 배열(18 × 160B)을 읽고, 대기자가 있으면 대기 큐 홉(새 머리는 CS당 20Hz 상한, 같은 머리는 0.25초마다), writer 스레드의 procfs stat(스레드당 20Hz 상한), 목격한 클라이언트 트랜잭션 슬롯의 클라이언트 pid 4B(트랜잭션당 20Hz 상한)를 더한다 |
| 표시 주기 | 기본 1초 (`--interval`) |
| 점유율·대기율 | 구간 샘플 중 점유/대기자가 관측된 비율 |
| 초당 진입·대기·손실 | 누적 카운터와 엔진 누적 획득 시간의 구간 차이 (32bit 넘침 보정; 누적 획득 시간(total_elapsed)과 진입 수가 함께 줄면 리셋으로 보고 새 값을 증분으로) |
| 소유자·대기 세션 | 구간 중 관측된 writer 와 대기 큐를 그 순간의 트랜잭션 번호와 클라이언트 pid 로 기억 — µs 단위 점유도 잡힌다. 엔진은 해제된 가장 낮은 슬롯부터 재배정하므로, 구간 중 클라이언트가 끊고 같은 슬롯을 다른 클라이언트가 받으면 구간 시작 때 신원으로 목격한 클라이언트를 `disconnected` 로 보인다(신원이 없으면 `pid N`) |
| 화면 | 터미널이면 요약 화면 제자리 갱신(`[r]` 녹화, `[l]` 한/영, `[q]` 종료), 파이프면 활동 행만 스크롤 |
| 판독량 | 평시 약 0.3MB/s (부록 B) |

## 4. 주요 기능 (Features)

### 4.1 SHOW CRITICAL SECTIONS 와 비교

같은 서버, 같은 부하(DDL 반복 + 병렬 INSERT)에서 수 ms 간격으로 찍은 출력이다.

```text
SHOW:    1  'LOG'  '1 writer'  0  3  4275  2  38106  17999  NULL  70.945  ...
cub_ctv: 1  LOG    1 writer    0  3     2  38106  17999  115  69404.6  70.945
           | owner  DBA@dbhost01 csql pid=3570914 login=cubrid ip=10.0.0.79  thr=4275  trid=141050
           | wq     thr=4227(tran 1 DBA csql) -> thr=4239(tran 3 DBA csql)  [2 of 3 waiting]
```

누적 값은 같은 엔진 카운터다(최대 대기 70.945ms 동일). SHOW 가 번호로 남기는 스레드·트랜잭션을 신원과 대기 체인으로
풀어 보여 준다. 순간 소유자와 대기자 수는 ms 단위로 바뀌므로 두 스냅샷이 다를 수 있고, 그 흐름은 라이브(4.2)가 보여 준다.

| SHOW 컬럼 | cub_ctv | 비고 |
|---|---|---|
| Index / Name | ix / name | 같음 |
| Num_holders | state | 같은 표기 |
| Num_waiting_readers / writers | waitR / waitW | 같음 (순간값) |
| Owner_thread_index | `thr=` | 같은 번호 체계 (실측 대조) |
| Owner_tran_index | tran + owner 줄 | 번호와 함께 클라이언트 정보 |
| Total_enter_count / Total_waiter_count | nenter / nwait | 같은 카운터 |
| Waiting_promoter_thread_index | wq 줄 | promoter 와 writer 대기 큐 전체 체인 |
| Max / Total_waiting_msecs | max_ms / total_ms | 같음 |
| — | reenter, 점유율·대기율·초당 진입/대기/손실, 판정, 트랜잭션 목록, 풀 집계, JSON, 기록·재생 | cub_ctv 만 |

### 4.2 라이브 (`-i`)

터미널에서는 구간마다 요약 화면을 제자리 갱신한다. 화면은 그리는 터미널 크기에 맞춰 배치하며(80칸 이상이면 폭을 넘는 줄 없음, 기록 재생은 재생하는 터미널 기준), 아래는 넓은 터미널에서 15초 경합 부하 중 한 구간이다(`tests/t9_quick_trace.sh` 실제 출력).


## 5. 제한 사항 (Limitations)

- 관측 범위: `critical_section.c` 에 등록된 동기화 객체만 보인다. 페이지 버퍼 래치, lock-free 구조, 트랜잭션 락(lock_manager)은 범위 밖이다. 읽기 SELECT 는 페이지 버퍼 래치를 쓰므로 여기에 거의 나타나지 않는다(스레드 대기 사유 집계로 그쪽인지만 알려 준다).
- 엔진 통계의 의미: nwait 는 무한 대기 경로만 센다. 대기 시간(total/max)은 획득까지 걸린 시간이고 보유 시간이 아니다. 소유자 트랜잭션은 writer 만 기록된다(reader 는 누구인지 모름). RWLOCK/RMUTEX 는 nwait 를 세지 않는다. 누적 카운터는 32bit. 엔진의 nenter 증가는 잠금 밖이라 경합 시 일부 유실되며, demote·promote 도 진입으로 센다.
- `;info csstat`: 엔진 누적 통계를 0으로 리셋한다(CS·RWLOCK·RMUTEX; 그 출력은 Total Wait 와 Total Reenter 열이 뒤바뀌어 찍히는 엔진 결함도 있다). cub_ctv 는 누적 획득 시간(total_elapsed)과 진입 수가 함께 줄면 리셋으로 보고 그 구간 증분을 새 값으로 계산하지만, 스냅샷의 누적값(nenter·nwait·max_ms 등)은 리셋 이후 값이다.
- 정지 없는 읽기: 카운터가 ±1 어긋날 수 있고, 대기 시간이 찢어 읽힌 순간 최대 +1,000ms 로 튈 수 있다. 점유율은 100Hz 분해능이라 µs 단위 점유에는 잡음이다. 개별 진입 이벤트는 잡지 않는다.
- 유도식: CS 의 rwlock·owner·promoter 큐·writer 큐 위치(통계 −96/−16/−24/−32B, I-4 로 교차검증), CS 의 tran(통계 −8B, 별도 검사 없음), SYNC_STATS 카운터 오프셋(nenter@16·nwait@20·nreenter@24·total@32·max@48 고정, type·name 만 검증), 스레드 엔트리 tran_index(index+28B 또는 +20B 중 검증 통과 1개, I-15), 통계 풀 청크 꼬리(I-12). 별도 검사가 없는 두 항목 외에는 교차검증을 통과할 때만 쓰고 실패하면 거부하거나 그 정보만 끈다. 11.4.5 서버에서는 tran_index 가 +20 후보로 I-15 를 통과하고, 경합 중 라이브에서 모든 불변식이 확정되는 것을 확인했다(유휴 스냅샷에서는 관측할 대기가 없어 I-18~I-20 만 미확정).
- 스트립된 라이브러리: `cubthread::Manager` 는 .symtab 에만 있는 지역 심볼이다. libcubrid.so 가 스트립되면 소유자 스레드·대기 큐·대기 사유가 꺼진다.
- 개인정보: 기록 파일과 디테일 덤프에는 클라이언트 신원(사용자·호스트·IP·프로그램명·OS 로그인명·클라이언트 pid), 대상 pid·DB 이름·라이브러리 경로, 스레드 이름·OS tid 가 들어 있고, 덤프에는 호스트명·커널 버전·실행 파일 경로도 들어 있다. 권한 0600 으로, 심볼릭 링크를 따라가지 않고 만든다. 이미 있는 이름은 내 소유의 링크 1개짜리 일반 파일일 때만 비우고, 아니면 거부한다.
- 권한·플랫폼: Linux(/proc), x86_64, 대상과 같은 호스트. `/proc/<pid>/mem` 읽기에는 서버와 같은 계정이 필요하고, Yama `ptrace_scope=1`(Ubuntu/Debian 기본)에서는 root 가 필요하다.
- 같은 이름의 DB: 같은 이름의 서버가 둘 이상이면 경고 후 첫 번째를 쓴다. pid 를 주면 그 서버를 본다.
- 검증 범위: CUBRID 11.5 공식·자가빌드 5개, 11.4.5, 11.3.3 은 전 기능 동작(경합 중 라이브 실측). 11.2.9 는 대기 사유·체인·스레드 상태(I-18~I-20)가, 10.2.18·11.0 은 거기에 더해 클라이언트 신원이 꺼지고 나머지는 동작한다(limitations '타 버전'). 그 밖의 버전은 미실측(불변식이 맞지 않으면 거부한다).

## 7. 빌드 (Build)

| 대상 선택 | DB 이름 우선(숫자 이름이 다른 서버 pid 와 같아도 DB 이름), 같은 이름 서버가 여럿이면 실행 안 하고 후보별 `--pid` 안내, `--pid` 는 pid 로만 선택 (t17, 서버 없이 실행) |
| 강등 보유 | HA 로그 플러시가 LOG 를 reader 로 강등해 쥔 구간을 데몬 보유로 셈: 점유 95% 구간에서 데몬 보유 3% → 95% (t18, 서버 없이 실행) |

| 입력 방어 | 손상·잘린 기록은 줄 번호와 함께 거부, 기록·덤프 파일 0600·심볼릭 링크 거부, 외부 문자열 정화 |

## 8. 사용 예 (Usage)

```sh
./cub_ctv -l                              # 실행 중인 cub_server 목록
./cub_ctv demodb                          # 스냅샷: 크리티컬 섹션 표 + 트랜잭션 표 + 풀 집계

./cub_ctv demodb -i --json                # 구간마다 JSON 1줄 (수집용)

./cub_ctv demodb -i --record incident.ctv # 현장: 본 화면을 기록 (라이브 화면에서 r 키로도)
./cub_ctv --replay incident.ctv           # 어디서든 재생 (서버 불필요)
./cub_ctv demodb --dump incident.json     # 그 순간 정보 전부 (장애 보고 첨부)
```

## 부록 A. 불변식 원장 (Invariant Ledger)

프로브 함수 = 불변식 1개. 거부 시 실패 id 가 오류에 실리고(`cannot validate SYNC_CRITICAL_SECTION layout (I-3 stats pointer) - refusing to guess`; ELF 단계 거부는 사유 문장만),
강등은 `layout:` 줄에 표시된다.

| ID | 불변식 | 실패 시 |
|---|---|---|
| I-0 | CS 배열이 읽힘(매핑 끝이면 축소 재시도; count 확정 후 그 크기로 재판독) | 거부 |
| I-1 | stride ∈ [96,256] 중 `cs_index@+8 == 0,1,2,3`이 성립하는 첫 값 | 거부 |
| I-2 | count = `cs_index == i ∧ 이름이 버퍼 안에서 NUL 로 끝나는 ASCII(0x21..0x7E) 문자열`인 연속 구간 길이 ≥ 4 (blob 밖은 직접 판독) | 거부 |
| I-3 | off_stats = 모든 CS에서 `*stats.type == CSECT ∧ stats->name == cs->name`인 유일 슬롯 | 거부 |
| I-4 | rwlock/owner/wq/pq = stats−96/−16/−32/−24(유도) + 대기수 ≤ 1e6 + 대기큐 포인터 범위 + `rwlock<0 ⇒ owner≠0`(writer 는 항상 owner 를 기록; demote·reader 퇴장은 owner/tran 을 남기므로 역방향은 검사하지 않음) 어긋난 CS ≤ 1 (무락 판독은 찢길 수 있어 배열을 다시 읽어 최대 3회까지 판정) | 거부 |
| I-5 | SYNC_STATS.type ∈ 1..4 (행별) | 행 `-` |
| I-6 | all_tdes = log_Gl 내 포인터로서 `tdes[k].tran_index == k` (k=0..3) | 강등: 트랜잭션 표·소유자 신원 없음, `layout:`에 사유. `--trans`는 사유 출력 후 종료 코드 1 |
| I-7 | 디스크립터 0·1번 포인터가 읽히고, TDES 간격 ∈ (0, 32768] 이면 그 간격을 디스크립터 스캔 상한으로 | 포인터 판독 불가: 강등(트랜잭션 표 없음); 간격 범위 밖: 상한 8KB 로 스캔(CLIENTIDS 는 I-9 로 따로 검증) |
| I-8 | trid@+4: 시스템 tran == 0 ∧ 다음 디스크립터 ≠ 0 | 강등: trid `-`, 해제 슬롯 필터 OFF |
| I-9 | CLIENTIDS strict: 문자열 6개(COW/SSO) 인쇄가능(ASCII 또는 정형 UTF-8) ∧ 내용 ≥ 1 ∧ pid ∈ [0, 2²²); 이미지 사전필터는 포인터·길이 범위만 | 후보 기각 |
| I-10 | witness(테이블 3등분 표본): 실패 ≥ 2 ∧ 실패 > 콘텐츠 합의일 때만 기각 | 후보 기각 |
| I-11 | trid == NULL_TRANID(−1)인 슬롯은 클라이언트 아님 | 행 숨김 |
| I-12 | 풀 청크 N: 전 엔트리 type ∈ 0..4 ∧ \|used−in_use\| ≤ 2 ∧ next ∈ {0, 유효} | 풀 뷰 생략 / 체인 끊김 표시 |
| I-13 | ELF: phdr/shdr/symtab/strtab 범위 ⊂ 파일 크기, entsize 정확 일치, UNDEF 제외 | 헤더·phdr/shdr 범위 위반·필수 심볼(`csectgl_Critical_sections`) 부재: 거부; 어긋난 심볼 섹션: 건너뜀; 선택 심볼(sync_Stats·log_Gl·Manager) 부재: 그 기능 강등 |
| I-14 | 스레드 엔트리 배열: Manager 객체 내 포인터로서 `index == 1,2,3,4`(엔진은 1부터 번호)인 (stride, off), 유도 필드(+28)가 엔트리 안에 드는 off만; count는 수열이 끊기거나 메모리가 끝날 때까지 | 강등: 스레드 정보 없음 |
| I-15 | entry.tran_index = index+28(스레드별 pgbuf 카운터가 있는 엔진) 또는 +20(이전 엔진) 중 전 엔트리 ∈ [−1, ntran) ∧ −1이 과반인 **유일** 후보 | 강등: 대기자 tran 없음 |
| — | 대기 세션: 샘플에서 대기 큐 머리를 본 순간 그 스레드 엔트리의 tran_index를 읽음(엔트리 검증 I-14 통과분만) | 미식별 = "tran ?" 아님, 목록에서 제외 |
| I-16 | entry.m_id = 비0 값이 전부 사용자 주소이고 서로 다르며 개수가 프로세스 스레드 수 근처(≤ 스레드 수+32)인 8정렬 오프셋 후보(≤64개) 중 I-17 이 OS tid 로 확인하는 것; I-17 이 불가하면 개수 ∈ [스레드 수−1−8, 스레드 수−1]인 **유일** 후보 | 강등: owner 스레드 없음 |
| — | 대기 체인: 엔진이 깨우는 순서대로 promoter 대기 큐(stats−24), 이어서 writer 대기 큐의 머리부터(두 큐에 같은 칸이 나오면 거기서 중단); 매 홉이 배열 내 엔트리(정렬·index 일치)이고 지금 CS writer/promoter 로 대기 중이어야 함(I-20 TS_WAIT ∧ 코드 9/11)(풀려나 페이지 래치 등에 다시 줄 선 스레드에서 끊음), 순환 시 중단 | 그 홉에서 체인 끝 |
| I-19 | entry.next_wait_thrd: resume_status 뒤 64B 안의 8정렬 오프셋으로서 전 엔트리 값이 0 또는 다른 배열 내 엔트리 포인터인 후보(≤8). 링크는 양 끝 스레드가 모두 지금 CS writer/promoter 로 대기 중(I-20 TS_WAIT ∧ 코드 9/11; I-20 없으면 코드 7..12)일 때만 셈(근처의 `tran_next_wait` 같은 락 대기 링크 배제). 프로브 이미지에서 그런 포인터를 보이는 **유일** 후보, 또는 대기 큐 홉 3회에서 단독으로 포인터를 보이고 다른 후보는 한 번도 보이지 않은 후보로 확정(그 전에는 홉마다 단독 후보를 그 홉에만 사용); 후보 없음이면 체인은 머리 1개 | 강등: 대기 체인 없음(머리만) |
| I-20 | entry.m_status: tran_index 와 resume_status 사이의 4정렬 필드로서 전 엔트리 0..4, 실스레드 전부 1..4, 실스레드 중 2(TS_RUN) 1개 이상인 **유일** 오프셋(+84 실측). 런타임 닻: CS 대기 큐 머리가 suspended 코드인데 TS_WAIT 가 아니면 불일치(이미 풀려난 머리는 셈하지 않음), I-18 과 같은 집계(64마다 절반 감쇠, 불일치 4회 이상이 일치보다 많으면)로 강등하고 그 오프셋은 재프로빙에서 제외. resume_status 는 마지막 사유를 남기므로 "지금 대기 중" 판단(스레드 대기 집계·체인 홉·I-19 링크)은 이 필드로; CS reader 대기는 TS_WAIT 없이 조건변수에서 기다리고 깨어난 뒤에도 코드 7 로 남으므로 그 수는 CS 의 waitR 합으로 센다 | 강등: resume_status 만으로 판단(지난 사유가 섞일 수 있음) |
| I-17 | OS tid: `m_id`(pthread_t)가 가리키는 struct pthread 안에서, 표본(최대 32개) 중 최대 8개를 뺀 나머지가 `/proc/<pid>/task` 의 서로 다른 tid 를 읽고(엔트리 풀 밖 스레드 허용) 전 실스레드에서 중복 없이 확인되는 **유일** 4정렬 오프셋(1KB 창). I-16 후보가 여럿이면 이 검사가 m_id 를 고른다 | 강등: 스레드 이름·디스크/CPU 행 없음 |
| I-18 | entry.resume_status: tran_index 뒤의 4정렬 필드로서 전 엔트리 값 ∈ [0,27], 실스레드에서 서로 다른 값 3종 이상·7 이상 도달·희소(값 종류 ≤ 최대값/2+1, 카운터 배제)인 **유일** 오프셋(여럿이면 suspended 코드 3,5,…,25,26 을 가진 하나); 유휴 서버처럼 값이 2종뿐이면 그 규칙(2종 이상·7 이상·희소)을 만족하는 유일 오프셋을 잠정 채택하고 스레드 생멸 때 3종 규칙으로 재프로빙. 런타임 닻: CS 대기 큐 머리 엔트리는 7..12 를 읽어야 함(엔트리를 읽은 뒤에도 큐 필드가 그 머리를 가리킬 때만 셈; 집계는 64마다 절반 감쇠, 불일치 4회 이상이 일치보다 많으면 강등하고, 이 오프셋 기준으로 찾은 I-19·I-20 도 함께 내려 다음 재프로빙에서 다시 찾음) | 강등: 스레드 대기 사유 없음, 체인은 머리만 |

설계 근거: CLIENTIDS 후보는 한 디스크립터의 strict 파싱만으로는 우연일 수 있어 다른 디스크립터
증인에서 같은 오프셋을 relaxed 파싱한다. 내용이 있으면 찬성, 전부 빈 값이면 무정보, 실패면 반대로
집계하고 "반대 2표 이상 ∧ 반대 > 찬성"일 때만 기각하므로 접속 중 레이스로 한 증인이 일시 실패해도
단독 거부권이 없다. 스레드 `m_id`는 유도가 아니라 스레드 수 불변식으로 프로빙한다.

## 부록 B. 서버 영향 실측 (Non-intrusiveness)

무침습의 정의: 서버의 **데이터·상태·실행 흐름을 바꾸지 않는다**(쓰기 0, CUBRID 락 0, 정지 0, 접속 0).
커널 수준의 자원 공유(B.1)는 남으며, 그 크기를 실측으로 적는다.

### B.1 `/proc/<pid>/mem` 판독과 mmap_lock

**커널 동작** (Linux 4.18 `fs/proc/base.c` `mem_rw()`, `mm/memory.c` `__access_remote_vm()`)

| 항목 | 사실 |
|---|---|
| 판독 단위 | `mem_rw()`가 요청을 **4KB 페이지 단위**로 나눠 `access_remote_vm()`을 반복 호출 |
| 잠금 | 호출마다 대상의 mmap_lock(4.18 명칭 `mmap_sem`)을 **읽기 모드**로 잡고, 1페이지를 가져와 복사한 뒤 바로 놓음 |
| 한 번 잡는 시간 | 페이지 1개 복사 시간, 실측 4~8µs (5.2MB 판독 = 약 1,270회 × 4~8µs = 5~11ms) |
| 서버와 겹치는 경우 | 서버의 **주소공간 변경**(mmap·munmap·mprotect: 큰 malloc, 스레드 스택 생성 등)이 쓰기 모드를 원할 때 그 페이지 1개 복사가 끝날 때까지 기다린다. 그 사이 서버의 다른 스레드 페이지 폴트도 그 쓰기 대기 뒤에 줄 선다 |
| 겹치지 않는 경우 | 서버의 일반 질의 경로(페이지 폴트 포함)는 같은 읽기 모드라 함께 진행된다 |
| 페이지 부재 시 | 판독은 `FOLL_FORCE`로 페이지를 가져오므로 스왑 아웃된 페이지를 읽으면 스왑 인이 일어난다. cub_ctv가 읽는 영역(CS 배열·트랜잭션 테이블·스레드 배열)은 엔진이 상시 쓰는 메모리라 상주해 있다 |

**모의 대상 실험** (운영 DB 무부하. 대상 = 5.2MB 상주 영역 + mmap/munmap 반복 스레드 + 페이지 폴트 반복 스레드,
판독기 = cub_ctv와 같은 패턴. 각 10초 × 2회, 단위 µs. 실험 하네스는 이 PR 에 포함하지 않음)

| 판독 패턴 | mmap+munmap p50 / p99 / p99.99 | 페이지 폴트 p50 / p99 / p99.99 |
|---|---|---|
