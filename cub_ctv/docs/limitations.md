# 한계 (Limitations)

| 영역 | 내용 |
|---|---|
| 관측 범위 | `critical_section.c` 체계에 등록된 프리미티브만. 페이지 버퍼 BCB 래치, lock-free 구조, lock_manager 트랜잭션 락은 범위 밖 |
| 엔진 통계 모델 | `nwait` 는 INF_WAIT 경로만 집계, `elapsed` 는 획득 지연(보유 시간 아님), `tran_index` 는 writer 만 설정(reader 주체 불명), RWLOCK/RMUTEX 는 nwait 미집계, 누적 카운터 u32. 엔진의 `nenter` 증가는 CS 잠금 밖의 비원자 연산이라 동시 진입 시 일부 유실되며, demote·promote(HA 모드의 LOG 플러시)도 진입으로 센다 |
| 통계 리셋 | `;info csstat` 는 엔진 누적 통계를 0으로 리셋한다. cub_ctv 는 누적 획득 시간(total_elapsed)과 진입 수가 함께 줄면 리셋으로 보고 그 구간 증분을 새 값으로 계산하지만(32bit 넘침과 구분), 스냅샷의 누적값은 리셋 이후 값이다 |
| 무락 판독 | 카운터 ±1, timeval 은 찢긴 판독에서 일시 최대 +1,000ms, occ% 는 100Hz 분해능(µs 점유는 잡음), 개별 enter 이벤트 미포착 |
| 유도식 | 아래 항목은 자체 프로브 없이 유도한다. 실패 시 해당 정보만 강등한다.<br>• CS: rwlock 3종(stats−96)·owner(−16)·대기 큐(writer −32, promoter −24) — I-4 교차검증 통과 시에만 사용<br>• CS: tran(stats−8) — 별도 검사 없음<br>• SYNC_STATS 카운터 오프셋(nenter 16, nwait 20, nreenter 24, total 32, max 48) — 고정값, type·name 만 검증<br>• `entry.tran_index = index+28 또는 +20`(둘 중 프로빙)<br>• 풀 청크 꼬리 |
| OS 측 (I-17/I-18) | `task/<tid>/io` 는 쓰지 않는다(0400). 로그 장치가 블록 장치가 아니면(overlay·NFS) await/util 은 없고 쥔 스레드의 D/R 비율만 쓴다. `resume_status` 는 실스레드의 코드가 1종뿐이면(기동 직후) 프로빙에 실패해 강등되고(재프로빙 일정대로 다시 찾으며 스레드 생멸 시 앞당김), 2종뿐인 유휴 서버에서는 유일 후보를 잠정 채택한다(CS 대기 큐 닻이 어긋나면 강등). 대기 체인 오프셋(I-19)은 시작 이미지에서 유일 후보가 보이거나 큐 홉에서 서로 다른 링크 3개가 한 후보에만 보이면 확정되며, 그 전에는 홉마다 단독으로 링크한 후보만 그 홉에 쓰고 후보가 갈리면 머리에서 끊긴다. 대기 사유 이름표는 11.4~현재 소스에서 같은 enum 값(0..27)을 전제로 하며 범위 밖 값은 강등으로 처리한다 |
| 스트립 빌드 | `cubthread::Manager` 는 .symtab 로컬 심볼 → 스트립된 libcubrid.so 에서는 스레드 정보(owner thr/대기 체인) 강등 |
| 플랫폼 | Linux(/proc)·x86_64, 대상과 동일 호스트. Yama `ptrace_scope=1` 에서는 사실상 root 필요 |
| 커널 상호작용 | `/proc/pid/mem` 판독은 4KB 페이지마다 대상의 mmap_lock 을 읽기 모드로 잡는다(1회 4~8µs). 서버의 주소공간 변경(mmap/munmap)이 그 시간만큼 기다릴 수 있다. 모의 대상 실험에서 라이브 판독량의 10배 이상에서도 검출되지 않음, 위험도 낮음 — PR.md 부록 B.1 |
| 판독량 | 시작 약 6.7MB 1회(스레드 배열 5.2MB 포함), 라이브 약 0.3MB/s — PR.md 부록 B.2 |
| 기록·덤프 파일 | 외부 전달 시 유의. 들어 있는 식별 정보는 다음과 같다.<br>• 트랜잭션 신원: 클라이언트 사용자·호스트·IP·프로그램명·OS 로그인명·클라이언트 pid<br>• 대상: pid·db 이름·libcubrid.so 경로<br>• 스레드: pthread id·OS tid·스레드 이름, 대기 큐 주소(`--record` 는 CPU 틱·대기 사유 히스토그램도)<br>• `--dump` 만: 호스트 nodename·커널 버전·실행 파일 경로 |
| 슬롯 재사용 | 엔진은 해제된 가장 낮은 트랜잭션 슬롯부터 다시 준다. 목격마다 슬롯의 클라이언트 pid 를 트랜잭션당 0.05초에 1회 읽어 구간 중 바뀐 클라이언트를 가르지만:<br>• 0.05초 안에 재배정되고 다시 목격된 슬롯은 그 간격 동안 앞 클라이언트의 pid 로 집계된다<br>• 한 구간 안에 접속했다 끊은 클라이언트는 신원이 없어 `pid N` 만 보인다<br>• 라이브 실행의 첫 구간은 직전 신원이 없어 떠난 클라이언트를 `pid N` 만으로 보인다<br>• JSON·`--detail` 의 소유자와 `--trans` 표는 현재 writer·현재 슬롯 기준이다 |
| 재생 범위 | 재생은 기록된 값만 다시 그린다. 라이브 기록에는 풀 집계가 없다(스냅샷 기록에만 있음). |
| 타 버전 | 11.5 공식·자가빌드 5개 배포본 실측. 11.4.5는 `entry.tran_index`(I-15)만 강등되고 나머지 정상. 10.x는 미실측(프로빙 실패 시 거부) |
| `--trans` 종료 코드 | 트랜잭션 테이블이 검증되지 않으면 사유를 출력하고 1로 종료한다(다른 모드는 강등 후 0) |
