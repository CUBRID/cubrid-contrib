# 아키텍처 (Architecture)

## 설계 원칙

0. **전제** — 서버를 띄운 CUBRID 설치 계정으로 실행한다. 그 권한으로 보이는 모든 서버 프로세스의 사용 내역을 비침습·최소 리소스로 보여주는 것이 목표이며, 모니터링을 위해 대상에 부하를 만드는 기능은 두지 않는다(부하 없이 정확히 못 보이는 값은 내지 않는다 — 그래서 최근 접근 비율(핫)이 없다).
1. **비침습 우선** — 서버를 멈추거나 디버거를 붙이지 않는다. **대상 프로세스에 쓰기가 없다.** 메모리 읽기는 커널이 읽은 페이지를 접근됨으로 표시하므로, 엔진이 원래 늘 만지는 메모리만 읽는다 — 페이지 헤더는 표본만, 대형 버퍼의 BCB 전수 스캔은 요청 시만([limitations](limitations.md#4-비침습성의-정확한-범위)). 락 0. 서버 요청은 대상 서버마다 `cubrid paramdump` 1회뿐이며(시작 시, 서버 재시작·기동 시, 대상 전환 시. 자동 재시도 없음 — 못 읽으면 `p` 전환 때 다시), 서버가 매핑한 설치본으로 비동기 실행해 화면을 멈추지 않는다.
   이 원칙은 기능 채택 여부를 실제로 가른다: 엔진 성능 카운터는 watcher가 있을 때만 도는데(엔진 설계), watcher를 만들려면 대상 메모리 쓰기와 서버 핫패스 비용이 생기므로 **만들지 않는다**. 대신 이미 돌고 있으면 읽고, 아니면 대체 지표로 내려간다.
2. **엔진 어휘로 표기** — OS 용어(`anon`, `file-backed`)가 아니라 `cubrid.conf` 파라미터·서브시스템 이름으로 보여준다.
3. **신뢰도를 숨기지 않는다** — 측정값과 추정값을 시각적으로 구분하고, 설명하지 못한 잔여를 화면에 남긴다.
4. **서버 무변경** — 파라미터 변경이나 재기동을 요구하지 않는다.
5. **자기검증 없이 값을 내지 않는다** — 오프셋 표는 후보일 뿐이다. 그 환경에서 검증을 통과하지 못하면 그 기능만 비활성하고 사유를 적는다(지어낸 값 금지).
6. **관측이 관측 대상을 위협하지 않는다** — 취합이 예산(0.5초)을 넘으면 그 프레임 값을 버리고 화면에 알린다. cgroup pids 여유가 없으면 외부 프로세스 실행을 생략한다.

## 데이터 소스 3계층

정확도와 침습도가 다른 세 소스를 목적에 따라 조합합니다.

| 계층 | 소스 | 얻는 것 | 침습도 | 비용 |
|---|---|---|---|---|
| **L1** | `/proc/<pid>/smaps`, `smaps_rollup`, `status`, `stat`, `task/`, `io`, `pagemap`, `/proc/diskstats` | 영역별 매핑/상주, 헤더 읽기 전 상주 확인, 프로세스별 RSS·PSS·swap, 폴트 수, 스레드 수, **디스크 I/O·IOPS·장치 util** | 없음(읽기) | µs~수십 ms (smaps 가 지배, 매핑 수에 비례) |
| **L2** | `cubrid paramdump` (CLI) | 컴포넌트별 **설정 할당량**, DB 페이지 크기 | 낮음(서버마다 질의 1회, 비동기) | 수십 ms |
| **L3** | `process_vm_readv` + `nm`/DWARF 심볼 | 엔진 전역 변수 상태 읽기 → 서브시스템별 실사용 | 낮음(정지 없는 읽기, 엔진이 늘 만지는 메모리만) | 전역 변수·버퍼풀 엔진 집계 µs, BCB 배열 수 ms (버퍼 슬롯 26만 개 이하일 때만) |

**L3에서 읽는 것**(2026-09 기준): 동적 메모리 서브시스템 전역(플랜/결과/필터 캐시·락·세션·카탈로그·연결·vacuum),
**버퍼풀 엔진 집계**(`pgbuf_Pool.buf_LRU_list[]` 의 존별 개수·victim 후보, `monitor.dirties_cnt` — 엔진이 늘 갱신),
**버퍼풀 페이지 슬롯 배열**(`pgbuf_Pool.BCB_table` → 슬롯별 VPID·dirty·LRU 존·`oldest_unflush_lsa`, 헤더는 표본 256개),
**로그 위치**(`log_Gl`의 append·nxio·eof LSA), 그리고 **엔진 성능 카운터**(`pstat_Global`, 이미 돌고 있을 때만).

> 대상에 쓰는 지점은 없습니다. 최근 접근 비율(핫)은 `clear_refs` 쓰기(대상 페이지 테이블 전수 순회)가 필요해 제공하지 않습니다.

## 수집 파이프라인

한 번의 샘플(`sample_once()`)은 아래 순서로 한 창(기본 0.5초)을 만듭니다. 라이브·1회 실행 모두 매 프레임 이 전체 과정을 수행합니다.

```
  ┌─ paramdump (시작 시·서버 재시작 시 1회, 매 프레임 비동기 회수) ► 설정 할당량
  │
  ├─ status / stat / io 읽기, diskstats              ┐ 기준선(t0)
  │                                                   ┘
  │        ── 대기 (--interval, 기본 0.5초) ──
  │
  ├─ smaps 전체 읽기 (대상 합계도 여기서)                   ┐
  ├─ status / stat / io / diskstats / meminfo / stat         │ 측정(t1)
  ├─ CUBRID 프로세스 탐색 1회 + status/stat (인스턴스·티어)   │
  ├─ 방법 B · 버퍼풀 엔진 집계 · BCB 배열과 헤더 표본 · 엔진 카운터 ┘
  │
  └─► 영역 분류 → 파라미터 귀속 → Δ 산출 → 렌더
```

### 프레임 비용

smaps 는 매 프레임 읽지 않습니다. 자기 소요 시간의 100배(벽시계 1%) 주기로 읽고(최소 `--interval`, 최대 60초), 사이에는 `status` 의 RSS·Swap 으로 합계만 갱신하며, 매핑 집합이 바뀌면(maps 해시) 10% 예산 안에서 앞당겨 읽습니다. 1GB 서버(6ms)는 약 0.6초, 100GB 서버(0.6~0.9초)는 60초 주기가 됩니다. /proc 전수 순회도 2초 주기이고 사이에는 지난 순회의 CUBRID pid 만 봅니다([limitations.md](limitations.md) 침습도 표). 그 외는 매 프레임 수행하며, 대기 시간을 뺀 수집 작업 시간은 대시보드 좌상단 `수집 N ms` 로 표시됩니다.
모든 값은 그 프레임에 읽은 현재 값입니다 — 이전 프레임의 값을 이어 쓰지 않습니다. 같은 값을 두 번 읽지 않도록만 줄였습니다.

| 항목 | 방식 |
|---|---|
| 대상 서버 합계 | 이번 프레임 smaps 를 읽으며 Rss·Pss·Swap·Clean 을 함께 합산(MAXREG 를 넘은 영역 포함). smaps_rollup 을 다시 읽지 않는다 |
| 프로세스 탐색 | `/proc` 를 한 번만 훑고 만나는 대로 처리한다. 프로세스 목록을 따로 두지 않고, 서버·PL·master·broker·CAS 수에 한도가 없다 |
| 다른 프로세스 | 다른 DB 서버·PL·master·broker·CAS 는 top·ps 수준(RSS·CPU)으로, 매 프레임 `status`·`stat` 을 읽는다. 페이지 테이블을 걷지 않아 프로세스당 수 µs 이고, CAS 가 수천 개여도 비용이 작다 |

| 조건 | 프레임당 수집 작업 (중앙값 / p90 / 최대) |
|---|---|
| 기본 | 29ms / 47ms / 53ms |

측정 환경: 64코어 호스트, CUBRID 11.5 인스턴스 2개(버퍼 512MB 1개), 라이브 대시보드 20여 프레임. 0.5초 간격 기준 약 6~8% 이며, 호스트 이웃 부하로 값이 흔들린다.
비용의 대부분은 분석 대상 서버의 상세(smaps, 페이지 헤더 수집, BCB 배열)이고, 주변 프로세스는 프로세스당 수 µs 다.
주요 항목은 smaps 읽기(커널이 smaps 를 생성하는 비용이라 매핑 수에 비례)와 버퍼풀 BCB 배열 읽기(버퍼 크기에 비례)입니다.
페이지 헤더는 표본 256개만 읽고, 버퍼 슬롯이 26만 개(16K 페이지 4GB)를 넘으면 BCB 배열 대신 엔진 집계(수십 KB)를 읽으므로
버퍼 크기가 커져도 기본 비용은 늘지 않습니다. 매핑이 많아 부담되면 `--interval` 로 간격을 늘립니다.

| 조건 (cbench, 버퍼 512MB = 32,768 슬롯, 라이브 10초) | cub_top 자신의 CPU |
|---|---|
| 기본 (헤더 표본 256개) | 0.37~0.39초 (약 3.8%) |
| 헤더 전수 (`--bcb-dump`) | 1.21~1.26초 (약 12%) |
| 대형 버퍼 기본 경로 (엔진 집계만, 시험 빌드로 경계를 낮춰 측정) | 0.29~0.31초 |

동적 힙 분해의 방법 B 는 매 프레임 수행합니다(방법 A 청크 히스토그램은 부하와 과대계상 때문에 제거).

## 계층 구조 모델

메모리를 4계층으로 봅니다. 위로 갈수록 확실하고, 아래로 갈수록 추정입니다.

```
L0  OS 전체                RAM · 사용 · 가용 · 페이지 캐시 · 스왑
     │
L1  CUBRID 프로세스 티어    server+master ─┬─ pl server (서버가 기동)
     │                                    
     │                     broker+CAS      (3-tier 별도 계층, 분리 가능)
     │
L2  cub_server 영역        data_buffer · log_buffer · dynamic-heap([heap] 포함)
     │                     thread stacks · code(.so) · bin/shm etc · glibc arena
     │
L3  dynamic-heap 내부      [B] plan/list/filter 캐시 · 락 · 세션 · 카탈로그 · 연결 (정확)
                           [A] 질의 작업버퍼 · db_private base · MVCC · 잔여 (추정)
```

프로세스 계층 주의: **PL 서버(`cub_pl`)는 cub_server가 기동하는 하위**이고, **broker/CAS는 3티어의 별도 계층**(별도 호스트로 분리 가능)입니다.

## 파라미터 관측성 3부류

`cubrid.conf`의 메모리 파라미터는 관측 방식이 셋으로 갈립니다. 이 분류가 도구 설계의 핵심입니다.

| 부류 | 성격 | 관측 방법 | 해당 파라미터 |
|---|---|---|---|
| **region** | 부팅 시 전용 영역으로 선할당 | smaps 익명 영역을 설정 크기로 매칭 → **직접 관측** | `data_buffer_size`, `log_buffer_size` |
| **stack** | 스레드별 예약, 대부분 미터치 | 가드 페이지 + 정확히 8MB 패턴 탐지 | (워커 스택 — `thread_stacksize`와 무관, [limitations](limitations.md) 참조) |
| **dynamic** | 요청·질의·세션마다 동적 할당 | 힙에 섞여 `/proc`로 개별 분리 불가 → **방법 B 필요** | `sort_buffer_size`, `max_plan_cache_entries`, `max_query_cache_entries`, `max_subquery_cache_size`, `temp_file_memory_size_in_pages` … |

## 자기검증 사다리 (버전 무관성의 근거)

CUBRID 판마다 구조체 레이아웃이 달라(실측: `pgbuf_bcb` 11.5=144B / 11.4.5=128B) 오프셋을 그대로 믿으면 거짓값이 나온다.
그래서 **표는 후보이고, 채택은 그 환경에서의 검증 통과**다.

```
버전 감지(.so 파일명 → rodata 문자열)
  ① 이 빌드의 표: 내장 표 → offsets/<버전>.tbl·내장 .tbl (버전 문자열 전체가 같을 때만) ─┐
  ② 그 .so 의 DWARF 런타임 추출(파이프로 받아 메모리에만, 라이브는 백그라운드)        │ 각 후보가 아래
  ③ 다른 빌드의 표: 기록된 루트 심볼 크기가 모두 맞고 paramdump 가 확인할 때만          │ 게이트를 통과해야 채택
  ④ 앵커 탐사(개수만)                                                                  ─┘
        ↓ 하나도 통과 못 하면
      해당 기능만 OFF + 사유 표기
```

`num_buffers` 는 모든 판에서 `pgbuf_Pool` 의 오프셋 0 이라, L4 만으로는 빌드를 가려내지 못한다.
그래서 표마다 루트 심볼(`pgbuf_Pool`·`lk_Gl`·`xcache_Global`·`log_Gl` 등 14개)의 ELF `st_size` 를 기록하고(`SYMSZ_*`),
실행 중인 `.so` 의 값과 대조한다(L1′). 예: `pgbuf_Pool` 11.4.x 656, 11.5.0.2374 648, 11.5.0.2543 592.
크기 기록이 없는 다른 빌드의 표는 채택하지 않는다. 크기는 필요조건일 뿐이므로(전역이 아닌 구조체의 변화는 잡지 못한다)
같은 빌드의 표가 없으면 다른 빌드의 표보다 그 `.so` 자신의 DWARF 를 먼저 쓴다.

| 게이트 | 검사 | 실패 시 |
|---|---|---|
| L1 심볼 | `.symtab`에 대상 심볼이 있는가 | 그 후보 탈락 |
| L1′ 크기 | 표에 기록된 루트 심볼 `st_size` 가 실행 중인 `.so` 와 같은가(다른 빌드의 표는 기록이 있어야 함) | 그 후보 탈락 |
| L2 정렬 | 오프셋이 4바이트 정렬인가 | 그 후보 탈락 |
| L3 골든 | 커밋된 골든 표와 소스 상수가 일치하는가(오프라인, `check-offsets.sh`) | CI 실패 |
| L4 교차 | `pgbuf num_buffers == paramdump data_buffer_pages` | 그 후보 탈락 |
| L4′ 위생 | `paramdump`가 없어도 `num_buffers`가 0 이하·비현실적 값이면 거부 | 그 후보 탈락 |
| L4″ 앵커 | (모든 후보) `css_Num_max_conn`·`lk_Gl.num_trans` 가 `max_clients` 로 정해지는 범위 안인가 | 그 후보 탈락 |
| L5 대조 | 버퍼풀: 페이지 헤더의 (pageid, volid)가 슬롯의 VPID와 맞는가 | 아래 참조 |

**L5의 시차 처리**: 슬롯 배열과 페이지 헤더는 읽는 시점이 다르므로, 그 사이 교체된 페이지는 필연적으로 불일치가 된다
(실측: 스캔 31~151ms 동안 최대 709건). 불일치분만 **BCB 전체와 헤더를 다시 읽어 짝지어 재검**하면 시차는 해소되고 오프셋 오류만 남는다. 교체된 레코드는 새 페이지의 상태(flags·존·oldest LSA)로 통째로 바뀌어, 한 레코드에 두 페이지가 섞이지 않는다.
판정은 재검 후 잔여로 하며, 잔여 5~50%는 검증된 레코드만으로 집계(`degraded`: 미검증 레코드는 집계·덤프·회전율 어디에도 쓰지 않는다), 50% 초과만 비활성한다.
헤더를 절반 이상 읽지 못하면 iopage 오프셋 오류로 보고 비활성한다.

## 관측 등급

화면의 모든 값 왼쪽에 한 글자로 신뢰도를 표시합니다.

| 기호 | 등급 | 뜻 |
|---|---|---|
| `●` | measured | OS 또는 엔진이 직접 보고한 값 |
| `◐` | reserved | 예약(매핑)만 확인된 값 — 실사용과 크게 다를 수 있음 |
| `◌` | estimated | 크기 패턴 등으로 추정한 값 |
| `?` | unattributed | 아직 귀속되지 않은 덩어리 |

## 모듈 구성 (`src/cub_top.c`, 단일 파일)

```
이식성 계층    CAP 런타임 탐지 + vmread(syscall→pread 폴백)
/proc 파서     parse_smaps / parse_rollup / parse_status_stat / parse_procio / parse_diskstats
설정           run_paramdump(창과 겹쳐 실행) / params_from_conf(서버 미기동 폴백)
심볼           sym_lookup — ELF .symtab 직접 파싱(binutils 불필요)
분해           method_b(전역 상태 읽기 + 4층 하니스) / method_a(청크 워크, 헤더 집어읽기)
분류           classify_regions — 영역 7종 + method_a 이중계상 방지용 버퍼 영역 노출
수집           sample_once — 1회 실행·라이브 공용(창 규약 단일 출처)
렌더           render_tree / render_terse / render_dash(canvas·braille·TUI)
```

수집은 `sample_once()` **하나**만 존재합니다. 1회 출력과 라이브 대시보드가 같은 함수를 쓰므로
두 경로의 값이 어긋날 수 없습니다. `tools/check-hist.sh` 가 이 동일성을 회귀로 검사합니다.

오프셋 표는 사람이 관리하지 않습니다 — `tools/dwoff` 로 바이너리에서 추출해 골든 표로 커밋하고,
`tools/check-offsets.sh` 가 소스 상수와 대조합니다.

## 용량 축 (수요 · 상한 · 헤드룸)

자원 판단을 "얼마나 쓰나"에서 "얼마까지 되나"로 넓히는 축이다. 전부 읽기 전용이며 취합 예산은 0.5초다(실측 0.2~0.9ms).

| 축 | 산출 | 비고 |
|---|---|---|
| 장치 | **DB 파일이 놓인 디스크**: 서버가 연 `<db>`·`<db>_*` 파일(fd 를 못 읽으면 `databases.txt` 의 볼륨·로그 경로) → `st_dev` → `/sys/dev/block` (없으면 마운트 원본 `/dev/…`, 그다음 `statfs` `f_fsid` — overlay 는 하위 파일시스템의 fsid 를 그대로 주고 XFS 는 거기에 장치 번호를 둔다) → 파티션은 상위 디스크, dm/md 는 `slaves` 를 따라 물리 디스크. 그중 가장 바쁜 하나 | 전부 설치 계정 권한으로 읽힘. 못 찾으면 장치 판정 생략·사유 표시 |
| 수요 | 그 장치의 IOPS(`diskstats` 델타) · 인스턴스 IOPS(`/proc/<pid>/io`) · 읽기/쓰기 B/s | |
| 지연 | `await = (rd_ticks+wr_ticks)/(rd_ios+wr_ios)` · 읽기/쓰기 분리 · 큐 깊이 | iostat와 같은 정의 |
| 상한 | **큐가 실제로 쌓인 순간**(평균 큐 깊이 ≥ 4)의 IOPS를 장치 고유 ID(wwid·serial·dm uuid + 크기)별로 기억. 큐 ≈1 의 직렬 스트림은 사용률 100%여도 지연을 잰 것이라 기록하지 않고, 대기가 길면 헤드룸보다 먼저 "지연 병목"으로 판정 | 이 실행 동안만 기억(파일 없음) |
| 헤드룸 | 현재 IOPS ÷ 상한 | 상한 미관측이면 그 사실을 표기 |
| 버퍼 효율 | 엔진 카운터가 돌면 `1 − ioreads/fetches`, 아니면 **BCB 회전율·재적재율** | 출처를 항상 병기 |

판정문이 이 값들을 조합해 **증설·축소·개선 중 무엇인지**를 한 줄로 낸다(용량 한계 / 지연 병목 / 버퍼 부족 / 재사용 거리가 버퍼 밖 / 과다 할당 / 여유, 프레임당 적재가 버퍼의 절반을 넘으면 신뢰도 낮음).
재적재율이 낮을 때는 "재사용 거리가 버퍼 밖"까지만 말한다 — 스캔(증설해도 줄지 않음)인지 버퍼의 수 배인 작업집합(증설하면 그만큼은 준다)인지
이 지표로는 가를 수 없어 "증설 무효"로 단정하지 않는다. 재적재율로 말하는 감소량도 하한이 아니라 LRU 를 가정한 추정치다.

## 영역 행 — 한 가지 축

값 4열(`alloc|rss|conf|grow`)과 게이지 하나(상주/할당)로 고정합니다. 이전의 보기 전환(`1` 할당/상주, `2` 설정 초과)은
핫(최근 접근) 축을 뺀 뒤 두 번째 보기가 `conf` 열과 같은 정보를 다시 보여 줄 뿐이어서 없앴습니다. 할당과 설정의 비교는
같은 행의 `alloc`·`conf` 열로, 1회 실행 트리에서는 `(설정 X, 할당 Y%)` 로 남아 있습니다.

## 기록과 재생 (record / replay)

라이브 화면이 렌더 시점에 `/proc` 을 읽지 않는다는 성질을 그대로 쓴다. 대시보드와 플롯은
`hist_push()` 가 채운 링버퍼와 `rp_apply()` 가 채운 구조체만 보므로, **그 입력을 파일에서
채우면 같은 렌더러가 같은 화면을 그린다.**

| | |
|---|---|
| 기록 포맷 | JSONL — 한 줄이 한 프레임, 키는 `-d`/`--dump-json` 과 동일 |
| 생성 경로 | `render_terse()` → `json_from_terse()` (**출력 경로를 새로 만들지 않는다**) |
| 재생 입력 | `rp_apply()` 한 곳에서만 프레임을 복원 |
| `/proc` 접근 | 0 — `--replay` 는 `enum_instances()` 앞에서 분기한다 |

기록이 별도 포맷이 아니라 기존 출력 그 자체이므로, 기록과 `-d` 가 어긋날 수 없다.
같은 이유로 `jq` 로 바로 다룰 수 있다.

**등급 표기**: 재생 중에는 좌상단이 `REPLAY n/N` 이 되고 시각이 **기록 당시 시각**으로 바뀐다.
관측 도구가 과거 데이터를 현재처럼 보여주면 안 되기 때문이다.

### 프레임 간 누적 상태

프레임 하나의 값만 복원하면 **여러 프레임에 걸쳐 쌓이는 값**이 매 프레임 초기화된다.
`rp_apply()` 가 구조체를 새로 채우기 때문이다. 다음이 함께 복원된다.

| 누적 상태 | 어디에 쓰이나 | 복원하지 않으면 |
|---|---|---|
| `SR[].prev_rss/ref/mapped` | 영역 `grow` 열 | 증감이 전부 `-` |
| `CAP2` + `g_cap_mtx` | 용량 판정문·상한 매트릭스 | 판정이 **반대로** 뒤집힘 |
| `PG` 존·볼륨별 상주 | 버퍼풀 상자 | 상자가 빈 채로 그려짐 |
| `B.it[]` | 동적 메모리 B 상자 | `B total 0B` |

영역 기준선은 **이름 기준**으로 이월한다. 인덱스로 이월하면 영역이 생기거나 사라지는 순간
다른 영역의 기준선을 물려받는다(`SR[]` 은 조건부로 채워진다 — `sr_by_name()` 주석과 같은 이유).

프로파일 칸(`prof_bs`/`prof_rw`)은 저장하지 않고 복원된 `req_kb`·`read_ratio` 에서 **재계산**한다.
저장값과 산출식이 어긋날 여지를 남기지 않기 위해서다.

**검증**: `tools/check-replay.sh` 가 기록 → 재생 → 재출력을 원본과 **모든 프레임, 양방향**으로 대조한다.
서버가 없는 환경(CI)에서는 이 빌드의 기준 녹화인 `examples/10-recording.jsonl`(cbench, `--interval 1`, 3프레임)을 같은 방식으로 **양방향** 대조한다. 키를 새로 쓰는 빌드는 예시를 재녹화해야 하며(검사가 그렇게 안내하고 실패한다), 그때 생략하는 것은 0.5초 간격 검사뿐이다.
재생이 빠뜨린 키, 녹화에 없던 키를 만들어 낸 경우(측정 불가를 0 으로), 값이 바뀐 경우가 모두 실패다.
비교에서 빼는 것은 실행 방법(`opts.used`)뿐이다. 녹화 호스트의 실행 상태(`perm.*`·채택 표·라이브러리 경로)와
엔진 초당 카운터도 녹화에서 복원하고, 출력된 값에서 계산하는 키(`cap.proc_iops`·`tier.server_cores`)는 라이브에서도
출력된 입력값으로 계산해 재생과 정확히 같다.
필드 하나를 고의로 빠뜨리면 그 키를 지목하며 실패한다(음성 테스트 확인).
