# 한계와 캐비엇 (Limitations & Caveats)

숫자를 해석하기 전에 반드시 읽어주세요. 이 도구는 **추정을 측정인 척하지 않는 것**을 설계 목표로 삼았고, 아래 항목들은 그 정직성의 목록입니다.

---

## 1. 환경 종속

| 항목 | 제약 |
|---|---|
| OS | Linux 전용. `/proc/<pid>/smaps`, `/proc/<pid>/pagemap`, `process_vm_readv` 의존 |
| 아키텍처 | x86_64 · i386 에서 `process_vm_readv` 시스템콜 번호를 직접 정의(구 glibc 대비). 그 외 아키텍처는 `pread` 폴백으로 동작 |
| 실행 계정 | **서버를 띄운 계정**(보통 `cubrid`)으로 실행한다. `smaps`·`pagemap`·`process_vm_readv` 는 커널 ptrace 검사를 받으므로 **동일 UID** 여야 하고, 다른 계정이면 55개 키가 빠지고 `perm.limited=1` 로 표기된다 → §15 |
| Yama `ptrace_scope` | **0 일 때만 전 기능**. 1(Ubuntu 기본)이면 같은 계정이어도 `process_vm_readv`·`/proc/<pid>/mem` 이 막혀 엔진 직독(방법 B·버퍼풀 페이지 슬롯·로그 LSA)이 꺼지고, 2·3 이면 마찬가지다. `smaps`·`io` 기반 축은 그대로 나온다. 사유는 `perm.reason` 에 나온다 → §15 |
| 검증 범위 | CUBRID 11.5, DB 페이지 16KB 환경에서만 실측 검증 |
| 메모리 영역 수 | 대상 프로세스의 매핑을 **4096개**까지 분류한다(스레드 약 700개부터 해당). 넘는 영역은 분류하지 않아 구성 합계가 총량보다 작아지며, 그 개수를 `limits.regions_dropped` 와 트리 출력 경고로 알린다 |
| 블록 장치 수 | 전체 장치를 **256개**까지 읽는다. 넘으면 `limits.disks_dropped` 와 트리 출력 경고로 알린다 |
| PSI | `/proc/pressure/memory` 는 커널 4.20 이상(또는 `psi=1`)에서만 있다. 없으면 `os.psi_mem_*=-1` 이고 메모리 압박 판정은 호스트 RAM % 로만 한다 |
| cgroup | v1·v2 모두 읽는다. 컨테이너 안에서는 `/proc/<pid>/cgroup` 의 경로가 마운트 아래에 없어 마운트 루트(= 자기 그룹)를 읽는다. 한도가 없으면(`max`, v1 의 무제한 값) 호스트 RAM 기준으로만 판정한다 |

## 2. 방법 B — 바이너리 종속성 (가장 중요)

구조체 오프셋과 심볼 이름이 **특정 CUBRID 빌드에서 추출된 값**입니다.

- 오프셋은 `libcubrid.so.11.5`의 DWARF에서 얻었습니다. **다른 버전·다른 컴파일 옵션에서는 달라질 수 있습니다.**
- `.c` 파일이 C++17로 컴파일되고 `pthread_mutex_t`(40B)·`std::mutex`·`std::atomic`·C++ 정렬이 섞여 있어, `SERVER_MODE` 조건부 필드 하나가 뒤 필드 오프셋을 전부 밀어냅니다.
- **잘못된 오프셋은 조용히 쓰레기 값을 냅니다.** 예: `vacuum_Worker_threads`(포인터)를 개수로 읽으면 **76.7GB** 같은 값이 나옵니다(그래서 64GB 초과 값은 `?` 로 강등).

**대응(4층 하니스)**: 오프셋은 이제 사람 손이 아니라 **바이너리에서 추출·대조**합니다.

| 층 | 검사 | 실패 시 |
|---|---|---|
| L1 구조 | 추출기의 CU 순회가 `cu_end` 에 정확히 착지 · 미지 abbrev/폼 없음 | 그 CU 결과 전량 폐기 |
| L2 위생 | sizeof 1B~1MB · 멤버 오프셋 < sizeof · **int32 오프셋 4바이트 정렬** | 방법 B 비활성(사유 표시) |
| L3 대조 | 소스 상수 ↔ 커밋된 골든 표(`tools/check-offsets.sh`) | 빌드/CI 실패 |
| L4 런타임 | `pgbuf.num_buffers == data_buffer_pages` · 개수 ≤ `max_clients`×8 · 값 ≤ 64GB | 항목 `?` 강등 + **합산 제외** |

`tools/dwoff` 로 `libcubrid.so` 에서 오프셋을 뽑아 기존 값과 대조할 수 있습니다
(11.5 실측: **14개 항목 전부 일치, desync 0**). 해소 경로까지 확증되었습니다 —
`lk_Gl+0` = `lk_global_data.config.num_trans`,
`sessions+12` = `active_sessions.states_hashmap.m_old_hash.m_freelist.alloc_cnt`.

**남는 한계**: 정렬이 맞으면서 틀린 오프셋은 값이 그럴듯해 **런타임으로는 구분할 수 없습니다**
(실측: 12→16 훼손 시 `alloc_cnt` 가 100→62 로 읽혀 상한 검사를 통과). 이 경우는 L3 대조가
잡으므로, 다른 버전에 옮길 때는 반드시 `tools/dwoff` 로 표를 재생성하십시오.

`vacuum_Worker_threads`(포인터)를 개수로 오독하면 **76.7GB** 같은 값이 나올 수 있고,
지금은 L4 의 64GB 상한이 이런 값을 `?` 로 강등하고 합산에서 제외합니다.

## 3. 비침습성의 정확한 범위

원칙: cub_top 은 **서버를 띄운 CUBRID 설치 계정**으로 돌며, 그 권한으로 보이는 범위를 **비침습·최소 리소스**로
보여준다. 모니터링을 위해 대상에 부하를 만드는 기능은 두지 않는다 — 부하 없이 정확히 보여줄 수 없는 값은 내지 않는다.

| 동작 | 침습도 |
|---|---|
| `/proc` 읽기 (status, stat, maps, pagemap, cgroup, pressure) 와 `/sys/fs/cgroup` | 없음 — 대상 페이지 상태를 바꾸지 않는다 |
| 볼륨 파일 `mincore` | 볼륨·로그 파일을 읽기 전용으로 열어 mmap 한 뒤 `mincore` 만 호출한다 — 페이지를 건드리지 않고(폴트·읽기 없음) 캐시 상주 여부만 받는다. 실측 GB당 약 7ms(12GB 85ms, 98GB 0.7초)라 소요 시간의 100배 주기(최소 10초)로 돌린다. 측정이 도는 프레임은 그만큼 길어지고(100GB 급이면 70초마다 0.7초), 용량 집계 예산(0.5초)과는 별도로 센다. 1회 실행(`-d`)은 매번 1회 측정한다. 설치 계정으로 열 수 있어야 하며 다른 계정의 서버면 미측정으로 표시한다 |
| `/proc/<pid>/smaps`(·`smaps_rollup`) | 커널이 대상의 mmap 읽기 락을 잡고 페이지 테이블을 걷는다. **실측 GB당 약 6~9ms**(1GB 서버 6ms, rollup 도 4ms로 큰 차이 없음) — 100GB 면 읽기 한 번이 0.6~0.9초. 그래서 매 프레임이 아니라 **자기 소요 시간의 100배 주기**(벽시계 1% 이내, 최소 간격·최대 60초)로 읽고, 사이에는 `status` 의 O(1) 합계(RSS·Swap)로 갱신한다. 매핑 집합이 바뀌면(`maps` 내용 해시, 페이지 테이블 안 걷음) 앞당겨 읽되 벽시계 10% 안에서만(매핑을 자주 바꾸는 서버가 매 프레임으로 되돌리지 못하게). 영역별 상주·PSS 는 마지막 읽기 값이며 화면 머리와 `server.smaps_age_s` 에 나이가 붙는다 |
| `/proc` 전수 순회(모든 pid 의 comm) | 2초 주기. 사이에는 지난 순회에서 찾은 CUBRID pid 만 다시 읽고(좀비는 끝난 것으로 봄), 하나라도 끝났거나 보던 서버가 내려가 있으면 그 프레임에 전수 순회. 그래서 재기동은 바로 따라가고, 사이에 생긴 다른 프로세스(새 CAS 등)는 한 주기 안에 나타난다 |
| `process_vm_readv` | 정지 없음, 쓰기 없음. 살아있는 메모리라 **torn read** 가능. 커널이 읽은 페이지를 **"최근 사용"으로 표시**한다(GUP `FOLL_TOUCH`) — 그래서 읽는 대상을 아래처럼 제한한다 |
| `cubrid paramdump` | 서버에 정식 접속(DBA 로그인) **1회**(시작 시·대상 선택 시·죽었던 서버가 다시 감지될 때). 못 읽으면 자동 재시도하지 않고, 시계열·대시보드 전환(`p`) 때 1회 다시 읽는다 |

### 읽기가 남기는 흔적과 대응

`process_vm_readv` 와 `/proc/<pid>/mem` 은 커널이 대상 페이지를 잡아 읽고 그 페이지를 접근됨으로 표시한다.
대상 메모리에 쓰지는 않지만 페이지 상태(referenced 비트·LRU 위치)는 바뀌고, 스왑아웃된 페이지는 다시 적재된다.
실측(4K 페이지 대역 프로세스): 16KB 마다 16B 를 한 번 읽으면 64MB 중 16MB(25%)가 `Referenced` 가 된다. THP 영역은 약 1%.

그래서 **엔진이 원래 늘 만지는 메모리만** 읽는다.

| 읽는 것 | 범위 | 이유 |
|---|---|---|
| 루트 전역 변수(방법 B) | 수 KB | 엔진이 매 요청 만지는 구조 |
| 버퍼풀 엔진 집계 | LRU 리스트 배열 수십 KB + `dirties_cnt` | 엔진이 fix·victim 마다 갱신. 버퍼 크기와 무관 |
| BCB 배열 | 버퍼 슬롯 26만 개(16K 페이지 4GB) 이하일 때만 매 프레임. 초과면 요청 시(`d`·`--pgbuf-detail`) | 슬롯당 144B 라 2M 슬롯이면 한 번에 300MB — 그 복사 자체가 부하 |
| 페이지 헤더 | 오프셋 검증용 **표본 최대 256개** — 엔진이 최근 쓴 LRU 존 1·2 에서 고르게, **pagemap 으로 상주를 확인한 것만**. 상주 여부는 프레임마다 새로 읽는다 | 헤더는 버퍼 페이지 안에 있어 읽으면 그 페이지를 건드린다. 스왑된 페이지는 건드리지 않는다. 차가운(존 3) 페이지는 존 1·2 표본이 32개 미만일 때만, 상주한 것으로 32개까지 채운다. 전수는 `--bcb-dump` 일 때만 |

실측(cbench, THP, 버퍼 512MB): `paramdump` 를 끈 1회 수집(`-d`, 방법 B·BCB 배열·헤더 표본·집계 모두 수행)의
프로세스 `Referenced` 증가는 유휴 2초 창과 구분되지 않았다(−2.8MB~+0.5MB). 같은 조건에서 `paramdump` 를
켜면 +12~15MB 로, 이는 서버가 질의를 처리하며 스스로 만진 메모리다(시작 시 1회).

### 최근 접근 비율(핫)을 보여주지 않는 이유

핫은 "창 안에 접근된 상주 페이지 비율"이다. 정확히 재려면 창 시작에 `/proc/<pid>/clear_refs` 로 대상의 접근 비트를
모두 지워야 하는데, 이는 대상 페이지 테이블 전수 순회(4K 페이지 상주 1GB 당 약 27ms)와 TLB 무효화를 일으키고,
메모리 집약 대역 실측에서 처리량이 52% 떨어졌다(73→35 Mpages/s). 4.2 미만 커널에서는 더 나쁘다 — `clear_refs` 가
`split_huge_page_pmd` 로 대상의 THP 를 4K 로 쪼개고, 순회 내내 `mmap_sem`(read)을 잡아 대상의 mmap/munmap 과 그 뒤의 fault 가 기다린다. 지우지 않고 `Referenced` 를 읽으면 우리 읽기와
커널 회수 주기가 섞인 값이 된다. 접근 비트를 건드리지 않고 재는 방법(`page_idle`·DAMON)은 설치 계정 권한으로는 쓸 수 없다.
부하 없이 정확히 잴 수 없으므로 **핫은 제공하지 않는다**. 버퍼풀의 쓰임새는 엔진이 스스로 유지하는 값 — LRU 존 분포,
victim 후보 수, dirty 수 — 과 회전율·재적재율로 본다.

### 외부 프로세스 실행의 안전성

`paramdump` 자식은 **셸을 거치지 않습니다**(`fork` + `execvp`, 인자 배열 직접 전달).

`popen()` 으로 명령 문자열을 조립하면 위험합니다. DB 이름은 `/proc/<pid>/cmdline` 에서 읽은
값이고 CUBRID 의 이름 검증(`check_database_name_local`)은 공백·`/`·`\`·`@` 만 거부할 뿐
**작은따옴표·세미콜론·`$`·백틱을 허용**합니다. 따라서 따옴표로 감싸도 셸 탈출이 가능했습니다
(PoC 로 임의 명령 실행 실증). `execvp` 는 셸 메타문자를 해석하지 않으므로 주입이
성립하지 않습니다.

실행 파일은 **서버가 매핑한 `libcubrid.so` 의 설치본**(`<설치>/bin/cubrid`)이고, `CUBRID`·`CUBRID_DATABASES` 는
서버 프로세스의 환경(`/proc/<pid>/environ`, 같은 계정이면 읽힘)에서 가져옵니다. 다른 버전의 클라이언트는 핸드셰이크에서
응답 없이 기다리기 때문입니다(11.4.5 클라이언트 → 11.5 서버: 20초 무출력 실측). 서버 라이브러리가 디스크에서 교체됐으면
(`(deleted)`) 버전을 보장할 수 없어 실행하지 않습니다. 항상 `-C`(클라이언트-서버)로 실행해 정지된 DB 를 단독 모드로 여는 일이 없습니다.

| 항목 | 동작 |
|---|---|
| 설치 위치 | 서버의 매핑(`<설치>/lib/libcubrid.so.N`), 없으면 `/proc/<pid>/exe` 가 `<설치>/bin/cub_server` 일 때 그 `<설치>`. 둘 다 못 읽으면 실행하지 않는다 — cub_top 을 띄운 셸의 `$CUBRID` 는 쓰지 않는다(다른 설치본의 `databases.txt`·`cub_master` 로 같은 이름의 다른 서버에 질의할 수 있어서) |
| 환경 | `CUBRID`·`CUBRID_DATABASES` 는 서버 프로세스의 것만. 환경을 못 읽으면 실행하지 않는다. 서버에 `CUBRID_DATABASES` 가 없으면 엔진 기본값과 같은 `$CUBRID/databases` 를 준다(cub_top 을 띄운 셸의 값이 아니라) |
| 실행 계정 | 서버를 띄운 계정으로 실행하므로 paramdump 도 그 계정·그 설치본으로 돈다 |
| 디스크립터 | 자식은 표준 입출력 외의 fd 를 모두 닫고 실행한다. `/proc/<pid>/mem`·pagemap 등 오래 여는 fd 는 `O_CLOEXEC` 로 연다 |
| `cubrid.conf` 선행 | 시작·대상 선택·재시작 때마다 paramdump 를 묻기 **전에** 서버의 `CUBRID`(없으면 설치 위치, 그것도 못 읽으면 cub_top 셸의 `$CUBRID`)의 `conf/cubrid.conf` 를 읽는다. paramdump 가 답하면 그 값으로 바뀌고, 생략·거부·무응답이면 conf 값이 남는다(`param.source`: `paramdump`/`cubrid.conf`/`none`) |

라이브에서는 **비동기**입니다 — 매 프레임 파이프를 논블로킹으로 거두고 자식은 `WNOHANG` 으로 회수하므로, `paramdump` 가
멈춰도 화면은 멈추지 않습니다. 10초(`PD_WAIT_MS`) 안에 끝나지 않으면 프로세스 그룹째 `SIGKILL` 하고(`setpgid` 로 손자까지),
최대 20ms 동안 기다려 그 자리에서 회수합니다. 디스크·NFS 대기처럼 커널 안에서 깨어날 수 없는 상태라 그 안에 죽지 않은 자식만
회수 목록에 남겨, 요청이 열려 있든 없든 매 프레임과 일시정지·도움말의 매 틱에서 `WNOHANG` 으로 거둡니다(막는 `waitpid` 는
그 대기만큼 화면을 세우므로 쓰지 않음). 프레임을 그리지 않는 일시정지(`space`)·도움말(`h`) 중에도 같은 틱으로 거두므로 이 기한은
지켜집니다. 출력을 닫고도 끝나지 않는 자식(파이프 EOF 뒤)은 그 자리에서 그룹째 종료합니다. 끝날 때는 경로와 무관하게 기다리던
요청을 정리합니다 — 라이브의 `q`·SIGINT·SIGTERM·SIGHUP·SIGQUIT, 1회 실행이 시그널로 끊길 때, 라이브·1회 실행의 비정상 종료(SIGSEGV 등)까지.
자식을 멈추는 핸들러는 모든 모드에서 첫 paramdump 를 띄우기 **전에** 설치되므로 라이브의 첫 프레임(간격, 화면 진입 전)에
끊겨도 남지 않습니다. 오류로 일찍 끝나는 경로(`--bcb-dump`·`--dump-json` 실패 등)를 포함한 모든 `return` 은 `exit()` 의 종료 처리기 하나가
기다리던 요청을 정리합니다. **정리할 수 없는 경우**: cub_top 이 `SIGKILL`·OOM killer 로 죽으면 어떤 처리기도 돌지 않으므로 paramdump
(서버에 대한 DBA 접속)는 자기 할 일을 마칠 때까지 남습니다. `Ctrl-Z` 로 정지된 동안에는 기한을 집행하지 않으므로 그동안 접속이 길어질 수 있고,
다시 `fg` 하면 다음 틱에 기한이 적용됩니다.
자식(paramdump·DWARF 추출)은 `fork` 직후 물려받은 핸들러를 기본값으로 되돌리고 부모의 자식 목록을 비우므로, 자식이 죽어도 부모의
다른 자식을 건드리지 않습니다. `fork` 부터 자식 pid 를 기록할 때까지는 INT·TERM·HUP·QUIT 를 막아 그 사이 시그널에도 자식이 남지 않습니다.
1회 실행(`-d`·`-t`)은 한 프레임에 값을 담아야 하므로 기한까지 `poll()` 로 기다립니다.
1회 실행은 사용자 정지를 수집 구간으로 나누지 않습니다. 측정 창 도중 `Ctrl-Z` 로 멈췄다 재개하면 그 한 프레임의 비율 값(CPU·I/O·폴트)은
정지 시간까지 포함한 평균입니다. 라이브(`-b`·`-p`)는 그 창을 버리고 다시 잽니다([views.md](views.md) "사용자 정지").

읽는 시점은 아래뿐입니다. 자동 재시도는 없습니다 — 못 읽으면 못 읽은 것으로 사유를 적고, 다시 읽는 것은 사용자 조작입니다.

| 시점 | paramdump |
|---|---|
| 구동 시 대상 인스턴스 결정 | 1회 |
| 대상 선택(`<` `>`, 1회 실행의 인스턴스 순회) | 선택마다 1회 |
| 죽었던 서버가 다시 감지됨(재시작) | 1회 |
| 시계열 ↔ 대시보드 전환(`p`) | 그 인스턴스 값을 못 읽은 상태일 때만 1회 |

구동 직후에는 최대 2회(시작 1회 + 실패 후 전환 1회)입니다. 실패 종류(접속 거부 — 부팅 중·`max_clients`·접근 거부,
무응답 10초, 실행 생략 — pids 여유 부족·라이브러리 교체·설치본 미상)는 모두 같은 규칙이며, 그동안 `cubrid.conf` 값을 씁니다.

실패 사유는 `param.skipped_reason` 과 화면 귀속률 자리에 남고, 그때 `param.*` 가 어디서 왔는지는 `param.source` 가 말합니다.

## 4. 도달 불가 / 미분리 항목

### 전역 루트에서 도달 불가
정렬 버퍼(`sort_param.internal_memory`), 해시조인·그룹바이 해시테이블, heap scan cache는 **질의 실행 컨텍스트와 스레드 스택**에 매달려 있습니다. 방법 B로 원리적으로 잡을 수 없어 `dynamic-heap` 의 미분해 잔여로만 보입니다.

### 알로케이터 계층 미분리
CUBRID는 glibc 위에 자체 계층이 있으나 현재 `db_private` 64KB base 블록만 라벨합니다.

| 계층 | 상태 |
|---|---|
| `db_private_alloc` (스레드별 dlmalloc mspace) | △ 64KB base만 라벨 |
| `area_alloc` (고정객체 풀, 블록 무반납) | ✗ 미분리 |
| `db_ws_alloc` (워크스페이스, quick_fit) | ✗ 미분리 |
| obstack / fixed heap | ✗ 미분리 (`#undef malloc`이라 memmon도 비추적) |

### 미반영 소비자
인덱스 스캔 작업버퍼, 통계 캐시, 세션 하위 객체(prepared statements·session variables·plan_string), deadlock WFG(`lk_Gl` 내 TWFG), VACUUM 로그 블록 버퍼는 아직 개별 귀속되지 않습니다. VACUUM은 구조체 184B만 확인됩니다.

## 5. `thread_stacksize`는 워커 스택이 아니다

**확인된 사실**: `pthread_attr_setstacksize(PRM_ID_THREAD_STACKSIZE)` 호출은 **heartbeat 경로 2곳에만** 존재합니다. 워커풀과 데몬은 `std::thread`를 사용하므로 **OS 기본 스택(보통 8MB, `ulimit -s`)** 을 씁니다.

따라서 `thread_stacksize × 워커수`로 스택 메모리를 계산하면 **틀립니다**. cub_top 은 `가드 페이지 + 정확히 8MB` 패턴으로 스택을 탐지합니다.

이 탐지도 휴리스틱입니다. `ulimit -s`가 8MB가 아닌 환경에서는 상수를 조정해야 합니다.

## 6. 서버 전체 메모리 상한이 없음 (엔진 특성)

CUBRID에는 **서버 전체 메모리 상한 파라미터나 `setrlimit`이 없습니다**(확인: 메모리 관련 `setrlimit` 사용 0, `memoize_memory_limit`은 쿼리 메모이제이션 한정). 유일한 총량 반응은 HA `applylogdb`의 자기 감시입니다.

파라미터는 대부분 **구조당/연산당 캡**이므로 `sort_buffer_size` 2M 같은 값이 **동시성 배수로 무계 증가**합니다. 즉 이 도구가 동적 힙 증가를 관측할 수는 있어도, "왜 이만큼까지 늘었나"의 상한 근거는 설정에 존재하지 않습니다.

## 7. 성장(growth) 관측창

관측창은 **현재 실행 세션 범위**입니다(링버퍼 최근 400 샘플, 0.5초 간격 시 약 3분). 박스 제목에 실제 창 길이를 표시합니다. 장기 추세(시간·일 단위)는 샘플을 파일로 적재하는 별도 수집 모드가 필요하며 현재 미구현입니다.

시간당 환산 증가율(`+X/h`)은 짧은 창에서 **선형 외삽**한 값이므로 창이 짧을 때 과대·과소로 흔들립니다.
라이브 링은 0.5초 × 800 = 약 6.7분이다. 더 긴 추세는 1분 평균 링(24시간)을 플롯 `w` 키로 본다. 분 평균이라 분 안의 봉우리는 눌린다.

## 8. 렌더링

- **동아시아 폭** — 캔버스 내부는 한글을 쓰지 않습니다. 한글 라벨을 넣으면 xterm 등에서 폭 계산이 어긋나 테두리가 깨집니다(실제 발생 이력). 한글은 캔버스 밖 범례에만 둡니다.
- **폰트 대체** — 일부 터미널 폰트가 꽉 찬 점자(`⣿`)를 다른 글리프로 대체해 폭이 어긋날 수 있습니다. 문제가 생기면 미터 글리프를 블록(`█`)으로 바꾸십시오.
- **최소 크기** — 96열 × 34행 이상을 권장합니다.

## 9. I/O 지표의 귀속 한계

| 지표 | 귀속 | 한계 |
|---|---|---|
| disk read/write, iops | **cub_server 정확** | broker/CAS/PL의 I/O는 포함되지 않음(서버 프로세스만) |
| cache absorb | 파생(정확) | `read_bytes`가 readahead로 `rchar`를 넘을 수 있어 1.0 클램프. **`rchar<64KB/s`(유휴)에서는 비율이 무의미해 `idle` 표기** |
| blkio wait | 중간 신뢰도 | **전 스레드 합**(delayacct_blkio_ticks, 스레드별 stat 합산 — 메인 스레드만 보면 항상 0)이라 100%%를 넘을 수 있음. 동기 대기만 계상되므로 0 을 "문제 없음"으로 단정하지 말 것. 등급 `●` |
| device util | **시스템 전체** | 컨테이너/오버레이 FS에서 DB 볼륨 → 블록 장치 매핑이 불가해 CUBRID 전용 값이 아님. 가장 바쁜 장치 하나만 표시 |

또한 rate 게이지는 **max(세션 피크, 절대 하한)** 대비입니다. 하한(8MB/s·200iops)이 없으면
유휴 시 미세값이 만충으로 보이고 프레임마다 점멸합니다. 하한 도입 후에도 실행 초기
피크가 낮은 동안은 상대값이 크게 보일 수 있으므로, **절대 판정은 `device util`(0~100%)** 로 하십시오.

## 10. 서버 미기동 시 동작 (중단하지 않음)

`cub_server`가 없어도 **중단하지 않고 관측 가능한 것만** 보여줍니다. 라이브 뷰에서는 서버가 내려갔다 다시 올라와도 계속 렌더하며 자동 복구합니다(pid가 바뀌면 심볼·라이브러리 경로를 재탐지).

| 항목 | 서버 미기동 시 |
|---|---|
| OS 컨텍스트(RAM·swap·cache) | ✅ 정상 |
| broker / CAS / master / PL | ✅ 정상 — 별도 프로세스라 서버와 무관하게 생존 |
| 장치 I/O(`diskstats`) | ✅ 정상 — 단 **시스템 전체값**, CUBRID 귀속 아님 |
| `cubrid.conf` 설정값 | ✅ **`paramdump` 대신 conf 파일 직접 파싱**으로 확보 |
| 영역별 할당/상주 | ❌ 프로세스가 없어 측정 불가 |
| 방법 B 힙 분해 | ❌ 불가 (`heapB.reason="cub_server 미기동"`) |
| 프로세스 I/O·성장 | ❌ 불가 |

표시 규약: 서버 행은 `? cub_server [미기동]`으로 등급 `?`, conf 설정값은 `◐`(예약)로 표시합니다. `-d` 출력은 `server.up=0`과 `conf.*` 키를 냅니다.

**CUBRID 프로세스가 하나도 없는 경우**에도 OS 컨텍스트와 conf 설정값은 출력됩니다.

## 11. 내장 memmon 미연동

CUBRID의 내장 메모리 모니터(`cubrid memmon`)는 할당을 **소스 `파일:라인`** 단위로 집계합니다. 이를 연동하면 동적 항목을 훨씬 정밀하게 나눌 수 있지만, `enable_memory_monitoring=yes` + 재기동 + 상시 태깅 오버헤드가 필요해 현재 미연동입니다. `파일:라인 → 서브시스템` 매핑 테이블이 추가로 필요합니다.

---

## 값을 신뢰해도 되는 순서

1. **`●` 등급** — `data_buffer_size`/`log_buffer_size` 상주량, 프로세스 PSS, 플랜 캐시(엔진 자체 카운터). 신뢰 가능.
2. **`◐` 등급** — 예약값. 매핑은 확실하나 실사용과 크게 다릅니다(예: 스택 예약 368M / 상주 796K).
3. **`◌` 등급** — 간접 산출 추정. 상대 비중만.
4. **`?` 등급** — 미귀속. 해석하지 마십시오.

## 확장 기능의 한계

| 항목 | 한계 |
|---|---|
| 한/영 자동 판정 | 로케일·커서폭(CPR)으로만 판정 — UTF-8 로케일 + 전각 폭이지만 글꼴에 한글 글리프가 없는 터미널은 감지 불가(두부 문자). `--ascii` 로 강제 |
| I/O 판정문 | wa 임계는 코어 수 비례(100/코어×0.5, 하한 0.5%). 장치 식별은 diskstats 최다사용 1개 — 컨테이너(overlay)는 백킹 장치를 못 찾을 수 있어 인스턴스 자체 I/O(≥1MB/s)를 근거에 포함해 오진을 막는다 |
| pids 안전장치 | cgroup pids 여유 <64 면 paramdump 생략(`param.skipped_reason`) — 그 프레임은 설정 대비 판정 축이 빠진다 |
| 재시작 재바인딩 | 같은 계정의 같은 DB 이름인 새 pid 로만 재접속 — 다른 계정에서 같은 이름으로 도는 DB 로는 넘어가지 않는다. DB 이름이 바뀌면 수동 재실행. 시작 시 이름이 겹치면 실행한 계정의 서버가 먼저다(`instance.<db>.uid`) |
| 심볼 이름 | 정확히 같은 이름, 또는 `이름.접미사`(`-flto` 의 `.lto_priv.N`)가 **하나뿐일 때**만 쓴다. 같은 이름의 접미사 객체가 둘 이상이면 서로 다른 객체라 어느 것도 쓰지 않는다. 함수·미정의 참조(`SHN_UNDEF`)는 제외 |
| DWARF 형식 | 읽는 것: 압축되지 않은 `.debug_info`/`.debug_abbrev`/`.debug_str`(DWARF 2~5, `strp`·인라인 문자열). 읽지 않고 사유를 그렇게 내는 것: 압축 섹션(`-gz`, `SHF_COMPRESSED`)·구형 `.zdebug`, 별도 파일의 디버그 정보(`.gnu_debuglink`), split DWARF(`.dwo`), dwz 공유 파일(`.gnu_debugaltlink`), DWARF5 문자열 색인(`strx`). 압축이면 `objcopy --decompress-debug-sections` 로 풀어 `tools/dwoff` 로 표를 만들어 `--offsets` 로 주면 된다 |
| 버전 사다리 | ⓑ DWARF 는 디버그 정보가 있는 빌드에서만(`--strip-debug` 면 ⓒ로). **`strip -s`(`.symtab` 제거)면 ⓒ도 불가** — `pgbuf_Pool`·`sessions`·`catalog_Hashmap`·`css_Num_*` 는 LOCAL 심볼이라 `.symtab` 에만 있고 `.dynsym` 에는 없다(`heapB.reason` 이 그렇게 말한다). ⓒ 앵커 탐사는 **앵커가 있는 항목만**(pgbuf 게이트, lock num_trans, conn max) 개수로 — xcache/session/catalog 카운터는 앵커가 없어 탐사 불가. **10.0 은 xcache/fpcache 구조 자체가 부재**(10.2+ 도입, 소스 태그로 확인)라 해당 항목은 어떤 방법으로도 없음 — "정보 최대 동일"의 자연 상한 |
| 정적 바이너리 | 빌드 glibc 의 NT_GNU_ABI_TAG 커널 하한 상속(본 산출물 3.2.0) — CentOS 6 배포는 el6 환경 빌드 필요 |

(구조가 11.x 와 달라 DWARF 로도 대상 멤버를 못 찾음). 지어내지 않고 생략/제외로 표기한다.

## 13. 버퍼풀 버퍼 제어블록(BCB) 상태 읽기의 한계

| 항목 | 한계 |
|---|---|
| 스냅샷 성격 | 래치 없이 배열을 한 번 읽는다 — 읽는 동안(수 ms) 바뀐 BCB 는 이전/이후 값이 섞일 수 있고, 틱 사이 변동은 보이지 않는다. 등급 ◌ |
| 버전 의존 | `pgbuf_bcb` 레이아웃이 판마다 다르다(11.5 144B / 11.4.5 128B). 표(`offsets/*.tbl`)에 BCB 키가 없으면 켜지지 않는다 — 10.0/10.1/11.0/11.2 표는 재수집 전이라 현재 비활성. 탐사(probe) 모드에서는 원리적으로 불가(앵커 없음) |
| dirty 의 의미 | "볼륨에 아직 안 썼다"이지 "커밋 안 됐다"가 아니다. 커밋은 로그만 내린다 |
| 해제된 페이지 | 삭제·해제된 페이지도 victim 될 때까지 BCB 에 남는다 — `cub_volmap` 의 `freed N` 표기가 이것(실측 demodb vol1 2,386 중 957) |
| 임시 페이지 | 질의가 끝나면 해제되지만 BCB 에는 남는다(cbench perm-temp 볼륨 2,096 중 1,141) |
| 대형 버퍼 | 262,144 BCB(16K 페이지 4GB) 초과면 배열 전수 통과는 매 프레임이 아니라 **자기 소요 시간의 100배 주기**(벽시계 1%, 최소 5초)로 돈다(2M 슬롯 300MB ≈ 100ms → 10초). 사이에는 마지막 통과의 상주·dirty·회전율·재적재율이 나이와 함께 서고, 매 프레임 **슬롯 1/64 표본**(버킷마다 해시로 고른 슬롯, 2M 슬롯이면 약 1MB)으로 적재량만 새로 잰다(`cap.miss_source="sample"`). 표본은 한 프레임에 두 번 바뀐 슬롯을 한 번으로 세므로 과소집계가 가능하고, 재적재율은 다음 통과에서 나온다. 요청(`d`·`--pgbuf-detail`·`--bcb-dump`)하면 매 프레임 전수 통과한다 |
| 엔진 집계 | LRU 리스트(공유+private)의 `count_lru1/2/3`·`count_vict_cand` 합과 `monitor.dirties_cnt`. 퍼프몬과 무관하게 엔진이 늘 갱신한다. 리스트를 순서대로 읽는 사이 값이 바뀔 수 있어 합은 근사(유휴 cbench·demodb 에서 BCB 스캔과 정확히 일치). 존 1(hot) 크기는 `pgbuf_lru_hot_ratio` 가 상한을 정하므로 "얼마나 뜨거운가"의 지표가 아니다. 오프셋은 표의 `OFF_PGBUF_LRULIST` 등 11개 키(10.1.8~11.5 로컬 7판 수집, 없는 표는 DWARF) |
| 페이지 헤더 표본 | 헤더는 표본 최대 256개(존 1·2, 32개 미만이면 상주 cold 로 채움, 프레임마다 상주 확인)만 읽는다. 오프셋이 틀리면 표본 전부가 불일치하므로 판정에는 충분하다. 상주가 아니어서 건너뛴 수는 `pgbuf.hdr_nonresident`, pagemap 을 못 읽어 확인 없이 읽은 수는 `pgbuf.hdr_pagemap_unchecked` |
| 페이지 헤더 대조 | BCB 배열(pass 1)과 페이지 헤더(pass 2)는 읽는 시점이 달라, 그 사이 교체된 페이지는 필연적으로 불일치가 된다(스캔 31~151ms 동안 최대 709건 실측). **불일치분만 BCB 전체·헤더를 다시 읽어 짝지어 재검**하면 시차분은 해소되고 오프셋 오류만 남는다(부하 중 잔여 0 실측). 교체가 확인된 레코드는 새 페이지의 flags·존·oldest LSA 로 통째로 바뀌고, 상주·dirty 집계도 다시 센다. 잔여가 5% 초과면 — 헤더를 전수 읽은 `--bcb-dump` 프레임에서 — 검증된 레코드만으로 집계(`pgbuf.degraded=1`: 미검증 레코드를 빼고 상주·dirty·볼륨별 수치를 다시 센다. 존 분포는 BCB 전체 기준이라 그대로. 그 프레임은 `--bcb-dump` 를 덮어쓰지 않고 회전율 계산도 건너뛴다), 50% 초과면 비활성. 헤더를 절반 이상 못 읽으면 iopage 오프셋 오류로 보고 비활성 |
| 권한 | `process_vm_readv` 는 방법 B 와 같은 권한(ptrace 스코프)을 요구한다 |
| 로그 LSA | `nxio_lsa` 는 `std::atomic<LOG_LSA>` 의 저장 바이트를 그대로 읽는다(8B 구조) — 표준 레이아웃이지만 컴파일러가 바뀌면 dwoff 재추출로 확인할 것 |

## 라이브러리 교체(재빌드) 직후의 실행 중 서버
서버가 매핑한 libcubrid.so 가 디스크에서 교체되면 maps 에 "(deleted)" 가 붙는다. cub_top 은 심볼·DWARF 를
`/proc/<pid>/map_files/<range>`(서버가 실제 실행 중인 옛 inode)에서 읽으므로 힙 B 가 그대로 살아 있다.
map_files 를 못 여는 환경(커널 < 4.3 — RHEL7 의 3.10 포함 — 에서는 설치 계정이 열 수 없다)에서는 디스크 경로를 쓰되,
**그 파일이 아직 실행 중인 inode 일 때만** 쓴다. "(deleted)" 이거나 inode 가 다르면 다른 빌드의 심볼을 읽게 되고 게이트로는
가려낼 수 없으므로 방법 B 를 거부하고 사유를 낸다(`heapB.reason`). 경로는 maps 줄의 나머지 전체라 공백이 든 설치 경로도
그대로 읽는다. `-d` 의 `heapB.lib` 로 어느 파일을 읽었는지 확인할 수 있다.

## 14. 용량 축의 한계

| 항목 | 한계 |
|---|---|
| 엔진 카운터 | `n_watchers > 0` 일 때만 엔진이 카운팅한다. watcher 는 우리가 만들지 않는다(무침습) → 평소에는 회전율 대체 경로다. 운영 중 statdump·`;histo on` 이 돌면 자동으로 perfmon 경로로 올라간다 |
| 회전율 대용 | 절대 히트율이 아니다. 분모가 '요청 수'가 아니라 '버퍼 크기'이므로 `hit_source` 를 반드시 함께 읽어야 한다 |
| 재적재율 | 라이브(프레임 2개 이상)에서만 낸다. 1회 실행은 `--bcb-dump` 파일을 기준선으로 회전율만 낸다(`cap.readmit_available=0`). 창은 최근 nbuf건의 내보내기다. LRU 에서 그 안에 다시 읽힌 페이지는 버퍼가 2배였다면 히트였을 미스이므로, 재적재율은 **2배 증설로 줄어드는 읽기의 추정치(LRU 가정)** 다. 정확한 LRU·균일 랜덤에서는 하한처럼 맞는다(작업집합 4·6·10·15배에서 29·18·11·7% vs 실제 34·20·11·7%). 그러나 하한이 보장되지는 않는다 — 프레임당 적재가 버퍼의 절반 이상이면 스냅샷 사이를 못 봐 과대·과소가 섞이고(화면에 '신뢰도 낮음'), CUBRID 의 중간점 삽입에서는 창이 세는 재사용 거리 (0.6B, 1.6B] 중 2배 증설이 돕는 것은 (0.6B, 1.2B] 뿐이라 실제보다 클 수 있으며, 접근 주기가 프레임 간격과 맞으면 적재 0 으로 보인다(앨리어싱, 감지 불가). `check-readmit.sh` 가 세 경우를 재현한다. 낮은 값은 "재사용 거리가 버퍼 밖"이라는 뜻일 뿐, 스캔(증설 무효)과 버퍼의 수 배인 작업집합(증설하면 그만큼은 준다)을 가르지 못한다 — 판정도 둘 중 하나로 단정하지 않는다. 창을 nbuf 의 여러 배로 넓히면 가를 수 있으나 그만큼 cub_top 메모리가 늘어(정확 집합은 내보내기 1건당 16B) 최소 리소스 원칙에 따라 넓히지 않았다. 프레임 사이에 내보내졌다 같은 프레임 안에 다시 읽힌 페이지는 보이지 않는다(그 비중이 큰 프레임이 위의 '신뢰도 낮음'). 메모리는 BCB 1개당 최대 약 80B(BCB 100만 개에 약 80MB) |
| 상한 | **큐가 실제로 쌓인 순간(평균 깊이 ≥ 4)을 한 번이라도 관측해야** 값이 생긴다. 직렬 스트림(깊이 ≈1)만 도는 장치는 사용률 100%여도 상한이 생기지 않고, 대기가 길면 "지연 병목(직렬)"으로 판정한다. 그 워크로드 패턴 기준이며 혼합비가 바뀌면 재관측이 필요하다. 합성 벤치로 재는 방법(보정 모드)은 무침습 원칙상 채택하지 않았다 |
| 상한의 키 | 장치 고유 ID(`dm/uuid`·`wwid`·`device/wwid`·`device/serial`)+크기. 이런 ID 를 내지 않는 장치(일부 가상 디스크)는 커널 이름+크기로 남으므로, 재부팅 뒤 같은 크기의 다른 디스크가 그 이름을 받으면 상한이 옮겨 붙을 수 있다 |
| 장치 귀속 | `cap.dev_iops`·`await`·큐는 **DB 파일이 놓인 디스크**(`cap.device`)의 값이다 — 디스크 단위라 같은 디스크의 다른 프로세스 I/O 는 포함된다. tmpfs·네트워크 파일시스템, ext4/btrfs 위 overlay(fsid 가 UUID 해시)처럼 블록 장치를 특정할 수 없으면 장치 판정을 하지 않고 `cap.device_reason` 으로 사유를 보인다. I/O 박스의 장치 util 은 이와 별개로 호스트 최다사용 장치다 |
| 취합 예산 | 0.5초를 넘으면 그 프레임을 포기한다 — 값이 비는 것이 오래 끄는 것보다 안전하다는 판단이며, 화면·`-d` 출력에 사유가 남는다 |
| 누적 히트율 | watcher 가 방금 붙어 fetch 표본이 1만 건 미만이면 내지 않는다(수십 건에서 0% 가 나오는 거짓 표기 방지) |

## 15. 실행 계정과 보이는 범위

대상 프로세스가 **다른 사용자 소유**면 커널의 ptrace 접근 검사로 일부 `/proc` 항목이 막힙니다.
cub_top 은 막힌 것을 0 으로 내보내지 않고 `perm.limited=1` 과 사유를 함께 표기합니다
(0 으로 내보내면 모니터링이 "메모리를 안 쓴다" 로 오독합니다).

### 관측 영역별 대조표

| 관측 영역 | 서버를 띄운 계정 | 다른 계정 | 차단 원인 |
|---|---|---|---|
| OS 전체(RAM·CPU 코어 점유·load·swap) | ○ | **○** | — |
| 장치 I/O(IOPS·await·큐 깊이·util) | ○ | **○** | — (용량 축은 DB 디스크, I/O 박스는 호스트 최다사용 장치) |
| CUBRID 프로세스 총량(VmRSS·VmSize·스레드 수) | ○ | **○** | `status` 는 소유자 무관 |
| 프로세스 CPU·폴트 | ○ | **○** | `stat` 는 소유자 무관 |
| `cubrid.conf` 설정값 | ○ | **○** | `paramdump`/conf 파싱 |
| 영역별 분해(`data_buffer`/`log_buffer`/동적 메모리 구분) | ○ | ✗ | `smaps` 차단 |
| PSS(공유 `.so` 배분 합계) | ○ | ✗ | `smaps` 차단 — 원리적으로 대체 불가 |
| 동적 메모리 상세 B(플랜/결과 캐시·락·세션·카탈로그) | ○ | ✗ | `process_vm_readv` EPERM → `heapB.enabled=0` |
| 버퍼풀 페이지 슬롯(볼륨별 상주·dirty·LRU 존) | ○ | ✗ | 위와 같음 → `pgbuf.enabled=0` |
| 로그 LSA·flush 부채 | ○ | ✗ | 위와 같음 |
| 용량 축의 버퍼 지표(히트율·회전율) | ○ | ✗ | 위와 같음 |
| 프로세스 귀속 I/O(`cap.proc_iops`·blkio) | ○ | ✗ | `/proc/<pid>/io` 차단 |

정리하면 **"이 호스트가 어떤 상태인가"와 "서버가 총 얼마를 쓰나"는 일반 계정으로도 보이고,
"그 안이 어떻게 쓰이나"는 서버를 띄운 계정(보통 `cubrid`)이어야 보입니다.** 그 계정이면 전 기능이 동작합니다(아래 Yama 제한이 없을 때).

**다른 계정의 서버에서도 나오는 것**: 호스트 전체(RAM·CPU·load·장치 IOPS·await·큐), 서버 **총량 RSS/VmSize**,
스레드 수, 프로세스 CPU, 인스턴스 목록, 용량 축의 장치 측 지표와 판정문 일부.

**나오지 않는 것**: 영역별 분해(data_buffer/log_buffer 구분), PSS, 동적 메모리 상세 A/B,
버퍼풀 페이지 슬롯, 엔진 통계, 프로세스 귀속 IOPS.

전체를 보려면 **서버를 띄운 계정**(보통 `cubrid`)으로 실행하십시오.

### 같은 계정인데 엔진 직독만 꺼질 때 — Yama `ptrace_scope`

`kernel.yama.ptrace_scope` 가 1 이상이면 커널이 **메모리 읽기(attach 모드)만** 추가로 검사한다.
`smaps`·`maps`·`io` 는 read 모드 검사라 그대로 열리므로, 위 표에서 `process_vm_readv` 가 원인인 행만 빠진다.

| `ptrace_scope` | 서버를 띄운 계정에서의 메모리 읽기 | 엔진 직독(방법 B·버퍼풀 페이지 슬롯·로그 LSA) |
|---|---|---|
| 0 | 허용 | 동작 |
| 1 (Ubuntu 기본) | 자기 자식 프로세스만 허용 — 서버는 cub_top 의 자식이 아니므로 거부 | 꺼짐 |
| 2 | 관리 권한 전용 | 꺼짐 |
| 3 | 전면 금지, 재부팅 전 변경 불가 | 꺼짐 |

엔진 직독이 필요하면 호스트가 `ptrace_scope=0` 이어야 한다. 그 밖의 축(영역 분해·PSS·프로세스 I/O·용량·CPU)은 값에 상관없이 나온다.

cub_top 은 시작 시(대상 전환·재시작 시에도) 대상의 매핑된 주소 1바이트를 실제로 읽어 본다. EPERM/EACCES 면 읽기를 끄고
`perm.limited=1` 과 사유(`perm.reason`, 예: `메모리 읽기 거부(EPERM): kernel.yama.ptrace_scope=1 …`)를 표기하며,
방법 B·버퍼풀 사유에도 같은 문장이 나온다. 2.6.32 계열은 `/proc/<pid>/mem` 을 tracer 에게만 허용하므로 폴백도 같은 판정이다.

## 재생(`--replay`)의 한계

| 항목 | 내용 |
|---|---|
| 재현 범위 | **기록된 키만** 재현된다. 기록에 없는 값은 재생에서 기본값(0 또는 "측정 안 됨")으로 나온다. |
| 인스턴스 전환 | 재생 중 `<` `>` 로 다른 DB 로 옮길 수 없다. 기록은 그 시점에 보고 있던 인스턴스 하나의 것이다 |
| 시각 | 화면의 시각은 **기록 당시** 값이고, 기록한 호스트의 시간대로 표시한다 — 재생하는 호스트의 시간대와 무관하다 |
| 기록 크기 | 프레임당 약 7KB. 0.5초 간격이면 시간당 약 50MB 이므로, 장시간 기록은 `--interval` 을 늘리거나 필요한 구간만 뜬다 |
| 호환성 | 기록은 `-d`/`--dump-json` 키 그대로다. 이전 빌드의 녹화는 지원하지 않는다 — 기록과 재생에 같은 빌드를 쓴다. 계층 메모리 키(`tier.*_rss_bytes`)가 없는 녹화(이전 빌드는 PSS 를 `*_pss_bytes` 로 기록)는 그 값이 0으로 재생되어 합계까지 틀리므로, 재생하지 않고 사유와 함께 종료 코드 1 로 끝낸다 |

재생이 라이브와 같은 값을 내는지는 `tools/check-replay.sh` 가 키 단위로 대조한다
(기록 → 재생 → 재출력, 모든 프레임·양방향). 비교 대상에서 빼는 것은 실행 방법 `opts.used` 뿐이다. 녹화에 없는 값은 재생에서도 미측정으로 남는다.
