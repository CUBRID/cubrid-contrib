# 한계와 검증 (Limitations & Verification)

## 1. 한계 (Limitations)

| 항목 | 내용 |
|---|---|
| 유지관리 범위 | **단독(standalone) 바이너리만 유지관리** — 트리 내 정식 유틸리티 등록은 참고 상태로 동결 |
| TDE 볼륨 | 암호 페이지는 내용 해석 불가 — **감지만** 한다 (`E` 표기 + `--check` 의 `note:` 줄, JSON `notes[]`). 암호화는 DB 의 속성이지 이상 구조가 아니므로 소견(finding)이 아니고 종료 코드 2 를 내지 않는다. 키 파일을 읽어 복호하는 것은 진단 도구의 권한 범위를 넘으므로 다루지 않는다 |
| 파일 탐색 | 기본은 엔진의 **파일 트래커**를 읽어 파일 목록을 얻는다(볼륨 0 헤더 `boot_hfid` → 부트 힙 첫 레코드 `trk_vfid` → 트래커 페이지, 10.1~11.5 공통). 각 단계를 자기검증(힙 헤더·`FILE_TRACKER` 헤더·16B 아이템)하므로 틀린 추측은 거기서 멈추고 예전 방식(예약 섹터 첫 페이지 프로브)으로 넘어가며, 출력 머리의 `files:` 줄이 어느 쪽이었는지 말한다. 트래커를 읽어도 **어느 파일도 소유하지 않는 섹터는 프로브**하므로 트래커에 없는 파일(삭제돼 vacuum 을 기다리는 파일, 만들어지는 중인 파일)도 찾는다. 같은 섹터를 두 파일이 주장하는 손상은 뒤에 읽은 파일이 이기고 앞 파일의 헤더 섹터는 프로브되지 않는다(`--full-sweep` 도 소유된 섹터는 보지 않는다) |
| 옆에서 도는 것의 감지 | `/proc` 만 읽는다. 감지하는 것과 못 하는 것의 목록은 [usage.md](usage.md#옆에서-도는-것의-감지-proc-만-읽는다). 못 하는 것: 11.1 미만 서버의 기동·복구 중 구분(등록 소켓에 pid 가 없어 `running, unverified` 로 적고 멈추지 않는다; 로그 락은 복구 전에 잡혀 단계를 가리지 못한다), 서버 내부 작업(vacuum·체크포인트·플러시), 다른 호스트의 유틸리티, `hidepid=2` 의 타 계정 프로세스, 유틸리티의 진행 단계. 컨테이너의 `/proc/diskstats` 는 호스트 전체 값이고, 오버레이 위의 볼륨은 장치를 찾지 못한다 |
| 라이브 스냅샷 시차 | 기동 중 DB는 더티 페이지 미반영분이 있어 순간적으로 할당>예약 같은 스큐가 보일 수 있다 — `--check`가 소견으로 알린다. **보정되지는 않는다**: `r` 새로고침은 다시 읽을 뿐이다. 메모리 쪽을 보려면 `--bufmap` 을 쓴다 |
| temp 파일 소유 트랜잭션 | 디스크에 기록되지 않는 런타임 정보 — 표시 불가 (생성 시각으로 대체). `FILE_HEADER` 에 트랜잭션/세션 필드가 없고(`FILE_DESCRIPTORS` 에도 temp 변형 없음) 소유 정보는 서버 메모리의 `file_Tempcache.tran_files[]` 에만 있다. 이를 읽으려면 `TR_TABLE_CS` 진입이 필요해 **락 0 원칙과 충돌** — 설계상 다루지 않는다 |
| 파일 핸들 | 배치: **동시 오픈 ≤ 2**(2슬롯 MRU 캐시, 투명 재오픈). 인터랙티브: 3스레드가 fd 를 공유하므로 **전 볼륨 fd 선개방·고정**(스레드 간 close 레이스 차단) |
| 스캔 I/O | 읽는 양은 README [실행 중 DB에서 쓸 때](../README.md#실행-중-db에서-쓸-때)의 읽기량을 보고 판단한다. 인터랙티브는 디스크 busy ≥ 80% 면 초기 스캔을 느리게 하고(슬라이스 512 섹터·50ms, 사이 200ms), 유틸리티·복구 중이면 멈춘다 — 자동 새로고침과 `--deep` 은 물러나지 않는다. `--deep` 은 예약 공간 전체를 읽어 운영 중 I/O 에 영향을 줄 수 있다 |
| 스레딩 절충 | 스캔 중 지도 색·카운터는 무락 판독(최악 = 한 프레임 늦은 표시). 'refreshed' 완료 문구는 커서 이동 중이면 인스펙션에 덮임(지도 갱신이 실질 신호). 인스펙션의 1페이지 pread 는 UI 동기(ms급) |
| 권한 | 볼륨 파일 읽기 권한이면 지도·`--check` 는 동작한다. `-m`·`--deep` 은 mincore(2) 결과를 쓰는데, 커널은 파일 소유자·쓰기 권한자·root 가 아니면 실제 상태 대신 "전부 상주" 를 돌려준다(`mm/mincore.c` `can_do_mincore`). 그래서 그 계정에서는 `-m` 을 "resident unknown" 으로 표시하고 `--deep` 은 거부한다 |
| 플랫폼 | 리눅스 x86_64 리틀엔디안 기준 (온디스크 포맷 자체가 LE). 단독 바이너리는 glibc-static 필요 |
| 버전 | **지원은 10.1 이상.** 10.1 미만(10.0·9.x) 볼륨은 읽지 않는다 — 10.1 재설계(CBRD-20185) 이전 구포맷. 로그의 릴리스로 판별해 시작 전·종료 시 경고하고 손상이 아닌 미지원으로 건너뛴다(종료코드 3). 10.1 이상은 **볼륨 파일 자체에서** 페이지 레이아웃을 판별해 처리한다(로그는 교차검증용이라 없어도 무방). 판별할 수 없으면 10.2+ 레이아웃을 가정하고 경고한다 — [ondisk-format.md §8](ondisk-format.md) |
| 빌드 의존 | 온디스크 구조체를 엔진 헤더에서 `#include` 하므로(오프셋 하드코딩 0 원칙의 대가) 헤더가 필요하다. **소스 체크아웃은 불필요** — `tools/build_fetch.sh` 가 헤더 23개만 내려받고 CMake 생성물(`config.h`·`version.h`)은 직접 만든다. 10.2~develop 6개 태그에서 빌드·실행 확인. 소스가 이미 있으면 `build_standalone.sh` 를 쓰되, 이쪽은 CMake 를 한 번 돌린 빌드 디렉터리가 필요하다 — [build.md](build.md) |
| 메시지 카탈로그 | cubrid.msg 미등록 — usage는 fprintf 직접 출력. 엔진 트리 밖에서 단독으로 배포되는 유틸이라 카탈로그에 묶지 않는다(UI 한/영은 `[l]` 토글이 담당) |
| dead version 판정 | HOME/NEWHOME 레코드만 집계 (BIGONE의 MVCC 헤더는 오버플로 페이지에 있어 제외) |
| `--bufmap` 층 | 스냅샷 파일 경유(직접 서버 메모리를 읽지 않음 — 무접촉 원칙 유지). 스냅샷 시각과 지도 시각의 차이만큼 시차가 있고, 미반영(DIRTY 또는 FLUSHING 비트) 표시는 "스냅샷 당시"다(페이지 박스의 LSA 비교가 현재를 말해준다). 두 비트가 모두 꺼져도 DWB 에서 볼륨 쓰기를 기다리는 페이지가 있을 수 있고, 그것은 LSA 비교로만 드러난다(`buf:clean unflushed (in DWB?)`). 해제된 페이지가 버퍼에 남는 것은 정상이라 `freed N` 으로 표기하고 90% 이상 불일치만 소견. db 이름이 다른 스냅샷은 거부. 포맷 계약 `CBCBMAP1` v1(32B 레코드) — cub_top 쪽 변경 시 함께 올릴 것 |

### 알려진 문제 (Known issues)

| 항목 | 내용 |
|---|---|
| 섹터 첫 페이지가 아닌 파일 헤더 | 서버 모드 `file_create` 는 HEAP·BTREE 를 만들 때 그 VFID 가 vacuum 의 dropped-files 목록에 아직 있으면 같은 섹터의 다음 페이지(또는 다음 섹터)를 헤더로 고른다 — DROP 이 커밋될 때 이미 진행 중이던 트랜잭션이 그 섹터로 테이블·인덱스를 만드는 경우다. 섹터 첫 페이지만 프로브하던 탐색은 그 파일을 놓쳤고, 놓친 파일의 페이지는 할당에서 빠져 볼륨 idle(`idle_pages`, `--warn-idle`)에 들어갔다(재현 DB 의 vol 1: 할당 37·idle 987 → 2차 탐색 뒤 44·980). **해결**: ① 파일 목록을 파일 트래커에서 얻으므로 헤더가 어느 페이지에 있든 찾는다([파일 탐색](#1-한계-limitations) 행). ② 트래커를 못 읽을 때를 위해 1차 탐색 뒤 소유자 미상 섹터가 256개 이하이면 그 섹터들의 전 페이지를 자동으로 본다(`--full-sweep` 은 개수와 무관하게 전부). ③ 그래도 소유자가 없는 섹터는 지도에서 `_`(예약 후 빈 공간)가 아니라 `?`(소유자 미상)로 먼저 판정한다 — 할당 여부는 소유 파일의 파일 테이블에서 오므로 소유자가 없으면 알 수 없다. 실측 — 11.4.4 demodb·11.5 seongnam 에 이 경우가 1건씩 있었고 트래커 탐색이 바로 찾는다 |

## 2. 검증 매트릭스 (Verification)

| 항목 | 결과 |
|---|---|
| 수치 정합 | 독립 구현 레퍼런스와 파일 수·볼륨별 예약 섹터·할당 페이지 정확 일치 (89.8GB 실DB) |
| del/dead 카운트 | 독립 파이썬 오라클과 페이지 단위 대조 일치 (dead=1 페이지, del=27 페이지 실측) |
| 성능 | 읽는 양으로 적는다(소요 시간은 디스크에 따라 다르다). 콜드 97GB 배치·`-i` 탐색 완료 각 31MB(파일 트래커, 파일 76개). `--deep` 은 예약 공간 전체를 연속 순차 읽기 — 소요 = 예약 공간 ÷ 그 디스크의 순차 읽기 속도 |
| 파일 트래커 정합 | `tools/check-tracker.sh`: 10.1·10.2·11.3·11.4.4·11.4.5·11.5 의 DB 10개에서 트래커 탐색과 `--no-tracker` 프로브의 파일 집합·볼륨별 예약/미상 섹터·소견이 전부 일치. 프로브한 섹터는 1~61 대 53~796 |
| 옆 프로세스 감지 | `tools/check-procstate.sh`: 실행 중 서버 = running(등록 확인), 서버 없는 DB = not_running, `backupdb` 실행 중에는 배치 머리·JSON·`-i` 헤더(⏸ 일시정지)에 나타나고 끝난 뒤엔 사라짐, TDE note 는 findings 와 분리. 디스크 busy 는 스크립트가 아니라 수동 실측: `/dev/sdb` 위 사본에 `dd oflag=direct` 를 걸어 100%·262MB/s 검출, 헤더에 `disk sdb busy 100% - scanning slowly` |
| 락 영향 | `--deep` 전수 스캔 중 `cubrid lockdb`: 잡힌 객체 0 |
| 버전 호환 | 10.1 / 10.2 / 11.3 / 11.4 / 11.4.5 / 11.5 볼륨 실측 (11.1 은 포맷 동일 근거만 — 실물 미확보. 10.0·9.3 은 공식 배포본으로 만든 DB 에서 미지원 경고·건너뜀을 확인). 버전별 포맷 변천은 [ondisk-format.md §8](ondisk-format.md) |
| 상주율 정확도 | 캐시 비운 뒤 특정 구간만 캐시 적재 → 지도의 해당 구간만 배경색 (위치·비율 일치) |
| TUI 프레임 | write 는 행 경계(글리프-완결)에서만 — strace 전수 실측 최대 1.6KB(<pty 4KB), 부분 리페인트 누적 화면 == 전체 리페인트 화면 (행 diff 0) |
| 입력 응답 | 강제 콜드(90GB): refresh·스캔 중에도 키→프레임 ≤0.1s, 유휴 CPU 0.0%, 랜덤키 소크 10/10 클린 |
| JSON | `json.load` 파싱 검증, 테이블/인덱스명 해석 포함 |
| `--bufmap` 정합 | 볼륨별 buf 페이지 수 = cub_top `pgbuf.vol<N>.resident` (cbench 9/9, demodb 5/5 일치). 스냅샷 dirty 55장은 디스크 LSA 대비 전부 unflushed, 다른 db 스냅샷은 거부. `tools/check-bufmap-flags.sh`: DIRTY / FLUSHING / 둘 다 / clean 레코드 하나씩의 스냅샷에서 unflushed 3·flushing 2 |
| 빌드 | CUBRID 트리 릴리스·디버그 양 모드 + 단독 정적 바이너리. `-Wall -Wextra` 경고 0 |
| 버전 호환 빌드 | `build_fetch.sh` 로 **10.2 / 11.0 / 11.2 / 11.3 / 11.4 / develop** 6개 태그 빌드·실행 확인. 헤더 차이 3건(`memory_cwrapper.h` 부재 · lz4/lzo include · `pflag` 필드명)은 자동 처리 — [build.md](build.md) |
